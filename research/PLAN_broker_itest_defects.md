## 0. Как они нашлись, и почему это главное

`scripts/agent-broker-itest.cjs` **не запускается ни в CI, ни в `npm test`** — CI гоняет
`npm run typecheck` и `npm test`, а itest'ы висят отдельными скриптами (`itest:server`,
`itest:agent`). Оба дефекта ниже жили в зелёном на вид репозитории ровно потому, что единственный
тест, который их видит, никто не запускал автоматически.

Порядок исправления поэтому такой: **сначала CI (§3), потом дефекты**. Иначе через месяц здесь будет
третий.

## 1. Дефект A — отклонённый грант отвечает «неизвестный токен»

**Симптом.** `FAIL the CLI reports a denied grant as 92 (exit 91)`. Человек нажал **Deny**;
следующий вызов агента получает `401 unauthorized` вместо `403 denied`, и CLI печатает «unknown
token» вместо «человек отказал».

**Причина** (`grantRegistry.ts`, `prune()`): перед каждым `mint()` реестр удаляет **все** гранты со
статусом `denied`. Комментарий объясняет это так: «отклонённый грант терминален — он существует
только чтобы отказывать, а неизвестный токен отказывается точно так же, поэтому удаление ничего
наблюдаемого не меняет». Рассуждение почти верное, и ошибка ровно в слове «наблюдаемого»: **коды
разные** — 403 против 401, 92 против 91. Как только в окне минтится следующий грант, отказ
превращается в «не знаю такого».

**Почему это стоит починить, а не переписать тест.** Разница между «тебе отказали» и «твой токен
не существует» — это то, по чему агент решает, что делать дальше: в первом случае бессмысленно
повторять, во втором — стоит попросить новый токен. Сейчас агент, которому отказали, будет просить
новый токен и снова открывать человеку модал.

**Решение.** Не удалять отклонённые гранты в `prune()`; вместо этого держать их как надгробие —
достаточно `{secret, status:'denied'}` без остальных полей, с отдельным ограничением на число.
Вытеснять их только когда кончилось место, и **после** pending-грантов. `lookup` для такого
возвращает `denied`, а не `unknown`.

## 2. Дефект B — параллельный exec удаляет чужой ключ

**Симптом.** `FAIL a finished exec leaves a concurrent one its key file (the key was deleted while
another exec was still running)`. Два одновременных `ssh:exec` по одной записи: первый завершается,
его `finally` удаляет материализованный ключ — и второй, ещё живой, теряет файл под собой.

**Первоначальный диагноз был неверен, и это важнее самой починки.** План утверждал, что два вызова
делят один путь к ключу. В коде это давно не так: `sshUseActions.ts:106-110` уже даёт каждому вызову
собственное имя — `` `${source.keyEntityId}-${crypto.randomUUID()}` `` — с комментарием, объясняющим
ровно эту опасность. Продакшен-код был исправен.

**Настоящая причина — в самом тесте.** Хелпер `keyFiles()` в `agent-broker-itest.cjs` читал
`keys/` **без рекурсии**, а ключи с тех пор живут в `keys/<pid>/` (каталог на окно, чтобы одна
чистка не убивала чужой живой ключ — это записано в `materializedKeys.ts`). Значит `keyFiles()`
**всегда возвращал пустой список**, и это ломало три проверки сразу:

| проверка | ожидание | что было на самом деле |
|---|---|---|
| «a finished exec leaves a concurrent one its key file» | `length > 0` | всегда падала |
| «…and leaves no decrypted key on disk» | `length === 0` | **всегда проходила, ничего не проверяя** |
| «once both are done, no key material is left» | `length === 0` | **всегда проходила, ничего не проверяя** |

Тест, который не может упасть, хуже теста, который не может пройти: две из трёх проверок ключевого
материала были ложно-зелёными. **Решение:** `keyFiles()` обходит дерево рекурсивно.

## 3. Порядок сборки

1. **CI**: добавить `npm run itest:agent` и `npm run itest:server` шагами в
   `.github/workflows/ci-extension.yml`. Оба дефекта должны стать красными в CI **до** починки —
   это и есть доказательство, что шаг работает.
2. Дефект B: рекурсивный `keyFiles()` — продакшен-код не трогаем, он исправен.
3. Дефект A: unit-тест в `grantRegistry.test.ts` («после mint'а нового гранта отклонённый остаётся
   отклонённым») + починка + зелёный itest.
4. CHANGELOG (раздел Fixed), `module_extension.md` — одна фраза про надгробия отклонённых грантов.

## 4. План тестирования

- **Красный сначала, оба.** Для A — юнит: `deny(t1)`, затем `mint()`, затем `lookup(t1)` → должен
  быть `denied`, а не `unknown`. Для B — юнит: два «вызова» подряд получают **разные** пути к ключу.
- itest целиком зелёный локально и в CI.
- Для B — проверка, что после обоих вызовов не остаётся ни одного файла (существующий тест
  «once both are done, no key material is left» должен остаться зелёным).
- Ограничение на число надгробий: 300 отказов подряд не растят карту без предела.

- [x] `itest:agent` запускается в CI, и его падение красит сборку. `itest:server` **сознательно не

- [x] Дефект A имеет юнит-тест в `npm test`; для B тестом является сам исправленный itest (ошибка
      была в нём).
- [x] Отклонённый грант отвечает `403/92` сколько угодно долго после других mint'ов; надгробия
      ограничены `MAX_DENIED_TOMBSTONES = 64`.
- [x] Три проверки ключевого материала снова что-то проверяют.
- [x] CHANGELOG говорит, что это было сломано в выпущенных версиях.

## 6. Замечание о доверии к «зелёному»

Оба дефекта прошли ревью, релиз и несколько недель эксплуатации, потому что единственный тест,
который их видит, запускался вручную. Это не про эти две ошибки, а про то, что **тест вне CI — это
не тест, а документ**. Пункт A3 дорожной карты («itest'ы в CI») стоит закрыть этим же изменением.
