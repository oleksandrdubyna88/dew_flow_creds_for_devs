exists today?*

## Implemented plans

Newest first.

| Plan | Landed | What it delivered |
|---|---|---|
| [PLAN_headless_cli.md](PLAN_headless_cli.md) | 2026-08-26 | `creds`: the product's terminal half, outside VS Code entirely — .NET 10 Native AOT, all eight verbs, named grants (`Enable CLI Access…` plus a `POST /v1/alias/<action>` route), and window discovery through `endpoints/window-<pid>.json`. The binary holds no credential and can obtain none: there is no field in the protocol a secret could travel in, which is a property of the response types rather than a promise. `creds ls` was deliberately absent at first — an enumeration route lets a caller compute which names exist — and was added afterwards under the owner's recorded decision, because the CLI that most needs it runs on a Remote-SSH host where the registry lives on the machine at the other end and cannot be read from disk. Four RID builds ship on a `cli-v*` tag; the first release is 2.3–3.1 MB compressed, 6.8 MB on disk, and needs no runtime on the host |
| [PLAN_remote_broker_bridge.md](PLAN_remote_broker_bridge.md) | 2026-08-26 | The broker reached from somewhere that is not this machine: a second listener beside the loopback TCP one (a 0600 unix socket on POSIX, a named pipe on Windows), WSL served by interop-exec — the Linux `creds` detects WSL by two independent signs and hands the call to the Windows binary, relaying streams and exit code — and Remote-SSH served by an `ssh -R` forward. The socket's permissions on the remote are the boundary and we cannot set them: for a `-R` forward **sshd** creates the socket, so the server's `StreamLocalBindMask` governs and the client flags that appear to ask for it were measured doing nothing. So the bridge looks instead of assuming. Phase 4 waits on D1 |
| [PLAN_wsl_agent_relay.md](PLAN_wsl_agent_relay.md) | 2026-08-26 | An `ssh-agent` usable from inside WSL while the key stays on the Windows side and never crosses. Two new verbs in `src_cli/` and an address published by the extension; the agent answers signature requests, so what reaches the VM is a signature and never key material — the distinction the whole product rests on, made observable in the one place a person can watch it work |
| [PLAN_depends_on.md](PLAN_depends_on.md) | 2026-08-26 | An SSH host is unreachable without the VPN that opens its network, and the vault held both entries and nothing about the sentence joining them. An entity now says what it `dependsOn`: both ends wear one colour in the tree, and the entity depended ON grows a *Depended on by* sub-tree **beside** its version history — the coexistence is a test, not a hope. The colour is stamped on the TARGET, never on the edge, which is why "change it once and every dependent follows" needs no propagation code and cannot drift. Two things worth reading: colour borrowing is **one hop, never transitive** — pinned after a test of mine failed asserting the opposite, because in a vault where everything reaches one VPN the chain would paint everything alike — and a dangling reference is **kept, not swept**, since a deleted target may be one sync away from returning. Colouring a row's LABEL needed `FileDecorationProvider`, an API this extension had never used; it was built as a spike and looked at before anything was designed on top of it |
| [PLAN_ephemeral_secrets.md](PLAN_ephemeral_secrets.md) | 2026-08-26 | Entries that delete themselves — after an hour, a day, when VS Code closes, or once an agent has used them — through the single deletion path, so the secret, its revision history and a causal tombstone all go together. The deviation is the interesting part: *"until the window closes"* became a **lease the open window renews**, because a close handler never runs for a window that crashed, and the entry it promised to destroy would then outlive its own promise while still holding a working secret. `oneUse` is refused for an SSH key pair, which the broker never serves and so could never burn. Its tail is [PLAN_ephemeral_secrets_tail.md](../todo/PLAN_ephemeral_secrets_tail.md) |
| [PLAN_ai_context_masking.md](PLAN_ai_context_masking.md) | 2026-08-26 | Vault secrets redacted out of Exec Broker output before it can reach an AI's context, at one interception point that covers every action present and future. The clipboard half is recorded as **refuted rather than deferred** — VS Code exposes no clipboard-change event and Windows Clipboard History captures at copy time, so a watcher would be a promise the platform cannot keep — and is replaced by two on-demand scans. Two later defects are recorded in it: MSSQL passwords never entered the mask table (an existing test had pinned that as intended behaviour), and an entry name could smuggle instructions into the agent snippet |
| [PLAN_git_sync_transport.md](PLAN_git_sync_transport.md) | 2026-08-25 | A third transport beside the shared folder and the server: the encrypted vault in a private git repository, reusing the causal merge untouched — the clone is a cache, and a rejected push is the server transport's `412`. Two things it does not hide: a repository's log reveals *when* a vault changed however opaque the files are, and deleting a vault removes the file, not the history. History retention and the PAT path were deliberately left out. Its integration test, against a real bare repo, caught the one defect no unit test could — git rewrites line endings on checkout, which would have corrupted every vault stored on Windows |
| [PLAN_broker_itest_defects.md](PLAN_broker_itest_defects.md) | 2026-08-25 | Two defects that reached released builds and stayed there: a refused agent token answered *unknown* instead of *denied* once any later grant was minted (the registry swept every refusal), and three assertions about decrypted key material tested nothing because the test helper never looked inside `keys/<pid>/` — one could not pass, two could not fail. The plan's own diagnosis of the second was wrong and the correction is recorded in it. The finding worth more than either: the only test that drives the real broker ran in no CI, and now does |
| [PLAN_import.md](PLAN_import.md) | 2026-08-25 | Import from `~/.ssh/config` and from Bitwarden / 1Password / KeePass / LastPass / Termius exports — the migration cost the audit named as the main obstacle to adoption. Format detected by content, skipped rows always reported, fresh ids for everything. KDBX is deliberately absent, and the module says why: Argon2 is not in Node, and this extension has no runtime dependencies |
| [PLAN_generator.md](PLAN_generator.md) | 2026-08-25 | Passwords, passphrases and Ed25519 keys generated in the form. The passphrase list is exactly 256 words so "eight bits per word" is true rather than approximately true, and decoration that satisfies a composition rule is not counted as strength. A generated key never touches disk — which `ssh-keygen` cannot do by construction |
| [PLAN_hygiene_reports.md](PLAN_hygiene_reports.md) | 2026-08-25 | The health report: reused passwords, weak ones, unencrypted keys in `~/.ssh`, plaintext credentials in a workspace `.env`, and an opt-in breach check that sends five hex characters of a SHA-1 and nothing else. No finding ever contains the value that caused it — the first test in the file |
| [PLAN_polish_layer.md](PLAN_polish_layer.md) | 2026-08-25 | The convenience layer the UX audit found entirely missing: five keybindings, a go-to-credential picker that matches exactly what the tree filter matches, `viewsWelcome`, a walkthrough, and a status-bar item for the lock — the state that decides whether sync runs at all |
| [PLAN_connection_manager.md](PLAN_connection_manager.md) | 2026-08-25 | The connection-manager fields an SSH entity was missing — a jump host as a typed reference, -L/-R forwarding rules, agent forwarding, tags — and audit B10 closed: a first connection shows the host fingerprint before it is trusted, and a pinned key is enforced rather than warned about. The first attempt got the host-key rule backwards (accept-new on the human path too, weaker than ssh own default); its test caught it |
| [PLAN_ssh_agent.md](PLAN_ssh_agent.md) | 2026-08-25 | An SSH agent of our own: keys served from memory over a per-window socket (a named pipe on Windows), a confirmation in front of **every** signature that names what is being signed, `SSH_AUTH_SOCK` injected into new terminals, and Git commit signing with a key that exists in no file. Two findings came from verifying rather than reasoning — Git-for-Windows' MSYS `ssh-keygen` cannot reach a named pipe (so the config sets `gpg.ssh.program`), and the `-Y sign`/`-Y verify` round trip is what proves the signature encoding. "Load into a running agent" is deliberately not built |
| [PLAN_secret_references.md](PLAN_secret_references.md) | 2026-08-25 | `creds://` references and a masked run wrapper: a stored command or script names a credential instead of holding one, the value reaches only the child's environment, and everything the child prints is scanned for it. Deviated from the plan by keeping the broker's `env` verb as the documented weaker option rather than retiring it |
| [PLAN_totp.md](PLAN_totp.md) | 2026-08-25 | TOTP as a stored secret field with a live code in the viewer. The second deliberate exception to "the viewer never receives a secret" — the derived code travels, the seed never does — for the same reason the image preview was the first |
| [PLAN_v1_vault_migration.md](PLAN_v1_vault_migration.md) | 2026-08-25 | Retired the v1 vault envelope: every vault is written v3 (wrapped/HKDF, scrypt once at unlock) — a legacy PIN-only vault migrates on its next sync with the same PIN and no data loss, a new PIN-only vault is v3 from the first write, and backups convert on their next run keeping their own standalone PIN. Closes the deferred tail of the 2026-08-25 review's finding 4 |
| [PLAN_nas_sender_pki.md](PLAN_nas_sender_pki.md) | 2026-08-25 | Sender authenticity for the folder transport: Ed25519 signatures over a transcript that binds recipient, payload and the sender’s own key, pinned on first contact. Shipped with the ceiling stated rather than hidden — trust-on-first-use is weak against an attacker already in place, and only the out-of-band fingerprint closes that |
| [PLAN_agent_ssh_broker.md](PLAN_agent_ssh_broker.md) | 2026-08-24 | *Share with Claude Code…* — an AI coding agent can run commands on an SSH host and open its terminal without ever receiving the password or key: it holds a capability token, and the window that holds the credential runs `ssh` on its behalf, gated by a first-use consent modal and recorded in an audit channel. Two claims did not survive contact: `BatchMode=yes` under forced askpass (unproven, so the password branch avoids depending on it) and per-call key cleanup (a finished exec deleted the file a concurrent one was still using) |
| [PLAN_monorepo_consolidation.md](PLAN_monorepo_consolidation.md) | 2026-08-23 | Both products into one conventions-compliant repository: the submodule mount and .NET baseline, the move (134 MB → 614 KB), the server's test suite converted to in-process xUnit v3, CI for both halves separately, MIT licensing and Marketplace preparation, the one-command Docker stack with four TLS modes, and the review above. Three defects surfaced only by verifying rather than reasoning — a Linux-only first-boot crash from a root-owned bind mount, `nginx:alpine` having no `openssl`, and nginx's stock `default.conf` shadowing the API |

## Conventions

a plan between them, are defined in `.claude/rules/shared/common/planning-docs.md` and enforced in CI
by `plan-lifecycle.mjs`.
