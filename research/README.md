| [PLAN_one_use_serialized.md](PLAN_one_use_serialized.md) | 2026-09-11 | Audit #3, and the one to read about a test that counts instead of measuring. Two check-then-act gaps across `await` boundaries in one function: the call cap was checked before the body was read and counted after consent, and the broker SHARES one consent dialog between concurrent first calls on purpose — so under `maxCalls: 1` two requests both passed at zero uses and both ran. `reserve` is one synchronous step now, and `touch` is gone. The serious half is the other one: "until an agent uses it once" is an option in the entry form, the burn runs after the answer deliberately, and two concurrent calls — or two grants, since the MCP door mints one per call — used such an entry twice. A lane per one-use ENTITY fixes it, and the first implementation keyed it per TOKEN, which looks equivalent and is not: every call reuses one token, so ordinary entries serialised too. | [PLAN_first_write_conditional.md](PLAN_first_write_conditional.md) | 2026-09-11 | Audit #5. `If-Match` covered every write except the one that CREATES the vault, which is the write a new account makes — so two machines signing in the same afternoon both read 404, both wrote unconditionally, and the second silently replaced the first. The server had understood `If-None-Match: *` since conditional writes landed; no client ever sent it. The record worth the file is the FOURTH state, which the gate found by pulling on the plan's own retry sentence: dropping the version on a 412 leaves "nothing known", and nothing known means write unconditionally — so a retry that skipped the re-read overwrote exactly what the refusal had protected. `MUST_REREAD` refuses locally, because after a 412 there is no precondition the client can honestly state |
| [PLAN_broker_origin_guard.md](PLAN_broker_origin_guard.md) | 2026-09-11 | Not an audit finding — found in the re-verification of one, which is its own small lesson. The broker is a loopback HTTP server, and a web page in the person's own browser is also on loopback; nothing looked at `Origin` or `Host`. The alias door needs no token by design (a rate limit and the consent modal are its authorisation), and a cross-origin `fetch` with `Content-Type: text/plain` is a SIMPLE request, so a site somebody merely visited could raise that modal in their editor and — on Allow — run the stored command; the unauthenticated read routes handed a rebound page the alias and entry names it would need to try. The record worth the file is what the review gate corrected before a line was written: the plan framed `Origin` as the defence, and `Origin` CANNOT close rebinding, because a browser omits it on a same-origin GET and a rebound page IS same-origin. `Host` closes it, with the port. Four reviewers then predicted the named pipe would 403 everything; it does not, because `BrokerClient` composes the same `http://127.0.0.1:<port>` whatever transport carries it — checked against the WSL bridge rather than argued |
| [PLAN_vault_delete_verified.md](PLAN_vault_delete_verified.md) | 2026-09-11 | Audit finding #4, and the one to read about the difference between an order that is described and an order that is enforced. `DELETE /api/vault` said in its own comment that the login key is removed only once there is no vault left for it to belong to — and enforced it by sequence: `DeleteEverythingFor` returned void, swallowed a locked file without a log line, took no gate, and the endpoint answered 204 and removed the key regardless. On a corporate server every developer wrap is sealed to that key, so a vault outliving it is a vault nobody can open, and the route is SELF-SERVICE rather than an admin operation. The suite's own helper for this exact failure existed and had been applied to five sibling paths, never to the vault. Now the vault goes first and ALONE (a refusal that says "nothing else was removed" has to be true rather than nearly true), a 503 carries a sentence the client quotes verbatim, and the whole account deletion — vault, key, registry record — is one serialized unit under the per-person gate, which cost `OrgMembersStore` a non-reentrant entry point beside its gated one. The review gate found the gate released too early TWICE, in two successive designs; and one of the tests written for it passed against the unfixed code until it was rewritten to assert what the vault FILE was doing rather than whether the request had finished |
| [PLAN_mask_fail_closed.md](PLAN_mask_fail_closed.md) | 2026-09-11 | Audit finding #1, and the one to read about what "fail open" costs. The broker's promise is that an agent USES a credential and never sees it; a response body carries the child's stdout, so the masker is the only thing between a command that prints its own password and the agent that wrote that command. Every error building the table of values to redact was CAUGHT, and the original body went out with `hits: 0` — which in the audit line is indistinguishable from "there was nothing to mask". A deleted entry produced the same silence with no exception at all. The table is read before the action now: a storage read that will not answer refuses the call while there is still nothing to undo, which is the trade the old comment said it was avoiding and was in fact making in reverse. The record worth the file is the rotation case, which all three review vendors found this plan getting wrong before a line was written: a rotation stores its new secret DURING the run, so no earlier table can hold it, and the planned fallback would have masked the OLD credential while sending the fresh one in the clear. Only that case withholds — an ordinary command answers from a pre-run table that is complete by construction — and a withheld answer carries `actionRan: true`, because an agent that cannot tell "it did not happen" from "you cannot see it" retries, and here a retry rotates twice |
| [PLAN_envelope_mac_required.md](PLAN_envelope_mac_required.md) | 2026-09-11 | Audit finding #2, and the one to read for how a guard can exist and still not guard. The envelope MAC is the only thing authenticating a vault's list of unlock wraps — `headerAad` deliberately leaves `wraps` unbound, because adding a security key rewrites them around the same master key — and it could simply be deleted: an absent `mac` answered `missing` at every version, and `missing` does not stop a sync. Not a read (the payload still needs a key) but a DOWNGRADE: strip the security-key and recovery wraps, leave the PIN, and every device opens by PIN alone and re-signs that state. Two records worth the file. The review gate found the first fix keying on the version NUMBER, which is unauthenticated plaintext for v3 — a signed v3 relabelled `version: 2` with its `mac` deleted read as legacy AND still decrypted; closed by requiring the legacy KDF too, since v3 introduced HKDF and the MAC in the same release, so the relabel costs the attacker the file either way. And the change was half untested: removing the verification from `VaultKeys.remember` left the entire MAC suite and the entire sync suite GREEN, because "before the cache" — the actual finding — was asserted nowhere; the test written for it immediately found `tampered` being swallowed by the silent-PIN route's wrong-PIN catch, reintroducing the silence the finding is about |
| [PLAN_kdf_params_bounded.md](PLAN_kdf_params_bounded.md) | 2026-09-10 | Audit finding #6, and the prerequisite the envelope-MAC work declared for itself. Every sealed blob records the scrypt cost it was made with so a raise never orphans an older file — and read without a bound those three fields were equally an instruction from whoever could WRITE the file: `maxmem` caps the memory term `N·r`, and nothing capped `p`, which multiplies time at constant memory. Measured against a real default-cost blob rather than the audit's synthetic one, `kdfP: 128` held a thread for **40 seconds** before answering "wrong password", and a PIN wrap is opened by BACKGROUND sync with a stored PIN, so nobody had to click. An open now accepts only the two tuples this build has ever written — `ACCEPTED_SCRYPT` — and refuses before deriving anything; raising the cost later is a format event, tuple and version bump together, or an older build calls a legitimate newer file corrupt. The record worth reading is what the gate changed: the accepted set was a `2^14..2^18` RANGE in the first draft, which admits tuples nobody ever wrote and an attacker could; and five reviewers across two rounds asked whether the new bound would misreport a newer file, which it cannot because every envelope path parses the envelope first — rather than answer it a fifth time, that ordering became a test |
