# PLAN — `creds-mcp` из WSL: агент внутри дистрибутива и окно на Windows

> Status: **IMPLEMENTED, 2026-08-28.** Закрывает последний невыполненный пункт DoD родительского
> плана [PLAN_mcp_server.md](PLAN_mcp_server.md). Написан по-русски, как и родительский план.
>
> Проверено на настоящем Claude Code внутри Ubuntu (WSL2, ядро 6.18) против настоящего окна
> VS Code 0.80.7 на Windows: `claude mcp list` → `creds ✔ Connected`, `creds_list` вернул запись
> из хранилища на Windows.
>
> Опора: `src_broker_client/src/WslInterop.cs` (`WindowsBridge`), `src_cli/src/AgentRelay.cs` и
> `src_cli/src/RelayPipe.cs` — там этот мост уже работает для `creds`.

## Симптом

Claude Code часто запускается **внутри WSL**. Он стартует `creds-mcp` как свой дочерний процесс —
и этот процесс оказывается в дистрибутиве, а окно VS Code с брокером на Windows.

`127.0.0.1` внутри WSL2 — это loopback виртуальной машины, где ничего нашего не слушает. Значит:

- `Endpoints.DirectoryHere()` смотрит в `~/.config/Code/User/globalStorage/...`, которого в
  дистрибутиве нет (папка расширения — на Windows);
- даже найдя порт, `BrokerClient` до него не дотянется.

Итог, который увидит человек: агент говорит «нет открытого окна CredsForDevs», хотя окно открыто
на том же компьютере. Сообщение верное и бесполезное.

## Что уже готово

**Мост есть, его просто никто не зовёт.** `WindowsBridge` в `src_broker_client` стал инстансом на
бинарь именно ради этого случая:

```csharp
public static WindowsBridge Creds { get; } = new("creds.exe", BinaryOverrideVariable);
```

`creds` пользуется им двумя способами, и оба нужны здесь:

| способ | где | что делает |
|---|---|---|
| `Relay(args)` | `Program.Main` | перезапускает вызов на Windows, унаследовав потоки |
| `StartPiped(args)` | `AgentRelay` | запускает Windows-процесс с pipe'ами, которыми владеет вызывающий |

Целостность двоичных данных через этот мост измерена (2026-08-26): 64 КБ случайных байт вернулись с
тем же SHA-256.

## Решение

**`creds-mcp` внутри WSL перезапускает себя на Windows и качает stdio через interop.**

Это `StartPiped`, а не `Relay`: MCP — это долгоживущий JSON-RPC поток в обе стороны, а не вызов с
кодом возврата. Linux-процесс становится насосом:

```
MCP-клиент ──stdin──► creds-mcp (Linux) ──pipe──► creds-mcp.exe (Windows) ──loopback──► окно
           ◄─stdout──                   ◄─pipe──
```

### Что нужно сделать

1. **Свой `WindowsBridge` для этого бинаря.** `new("creds-mcp.exe", "CREDS_MCP_WINDOWS_BINARY")` —
   отдельная переменная окружения по причине, уже записанной в `WslInterop.cs`: указание одного
   бинаря на нестандартный путь не должно перенаправлять другой.
2. **Решение о перезапуске — до всего остального.** `WslInterop.ShouldRelayHere()` уже отвечает на
   этот вопрос двумя независимыми признаками (`WSL_DISTRO_NAME` и `/proc/version`) и содержит
   защиту от бесконечной рекурсии (`CREDS_RELAYED_FROM_WSL`). Проверять до `--help`? Нет: `--help`
   отвечает одинаково с обеих сторон и лишний процесс ради него не нужен.
3. **Насос на два направления, без переупаковки.** Байты идут как есть: JSON-RPC — это строки, но
   насос, который их разбирает, — это ещё одно место, где протокол можно сломать. `stderr`
   наследуется, чтобы диагностика с Windows-стороны доходила до клиента.
4. **Закрытие с обеих сторон.** Клиент закрывает stdin — насос закрывает stdin дочернего; дочерний
   умирает — насос выходит с его кодом. Ни один из двух процессов не должен пережить другой: MCP-
   клиент считает сервер живым, пока жив процесс, который он запустил.

### Чего делать НЕ надо

**Не пытаться найти папку endpoints из Linux.** Она есть на Windows, путь к ней зависит от версии
и издания VS Code, а `/mnt/c/Users/...` — догадка, которая сломается на первой машине с диском не
`C:`. Windows-половина уже умеет её находить; пусть она этим и занимается.

**Не заводить сетевой мост.** Ровно та причина, что записана в `WslInterop.cs`: ничего не должно
начать слушать в новом месте. Брокер остаётся loopback-only.

## Что вышло иначе, и что показала сборка

**Предсказание о буферизации было измерено и опровергнуто.** Насос писался в расчёте на то, что
`Process.StandardInput.BaseStream` — это `FileStream`, запрошенный с буфером 4 КБ, — придержит
JSON-RPC запрос в 154 байта до первого flush, и обе половины будут ждать друг друга. Проба против
настоящего бинаря на .NET 10: **запрос без flush дошёл, ответ вернулся.** Такого дефекта сегодня
нет. Пофрагментный flush в `CarryAsync` оставлен не как исправление, а как гарантия: этот процесс
несёт чужой протокол, и «короткая запись доходит до другого конца» иначе становится свойством
внутренней стратегии рантайма, которое ни в каком контракте не записано и уже переписывалось.
`AgentRelay` пользуется обычным `CopyToAsync` и по той же измеренной причине работает — это
осознанное расхождение, а не забытое.

**Интеграционный тест сделан на настоящем WSL, а не на эхо-скрипте.** План предлагал гонять насос
без WSL, подсунув `CREDS_MCP_WINDOWS_BINARY` фальшивый бинарь. Это невозможно тем способом, каким
было записано: `ShouldRelay` коротко замыкается на `isWindows`, так что на Windows решение о
перезапуске не наступает вообще, и подделать его нечем, кроме тестового чёрного хода в продакшн-код.
Поэтому проверка разделена честно: **юнит-тесты** (`WslPumpTests`) закрывают два окончания насоса на
потоках без всякого процесса, а **`scripts/creds-mcp-wsl-itest.cjs`** собирает Linux-бинарь внутри
дистрибутива и гоняет полный обмен против настоящего брокера — громко пропускаясь, когда WSL,
Windows-бинаря или .NET SDK нет.

**Зубастость обеих проверок доказана саботажем.** Замена `CarryAsync` на голый `CopyToAsync` кладёт
юнит-тест с буферизованным приёмником («ничего не дошло»); снятие самого моста в `ServeAsync` кладёт
8 проверок интеграционного теста ровно тем симптомом, ради которого мост и писался —
*«1 window(s) announced themselves but none is listening now»* при открытом окне.

**Попутно нашлась поломка соседа.** `scripts/creds-mcp-itest.cjs` падал 19 проверками на master:
параметр `visibleConfig` вставили в конструктор `CredsAgentServer` (32d8f01, 2026-08-27), а
позиционные аргументы скрипта не сдвинули — гейт стал поставщиком конфигов, и каждый вызов уровня 2
отвечал «no window answered». Скрипт не гоняется в CI, поэтому месяц этого никто не видел. Починено
одной строкой `undefined` с комментарием, объясняющим, откуда считать в следующий раз.

**`--help` и ошибка аргумента отвечаются на Linux-стороне.** Решение вынесено в чистую
`Program.Classify`, потому что из чтения `Main` оно не очевидно: обе половины печатают один и тот же
текст, а release-проверка это как раз `--help | grep creds_list`.

## Что осталось открытым

- **Кнопка «Install the MCP Server…» ничего не знает про WSL.** `ridFor(process.platform, …)` всегда
  даёт Windows (расширение `extensionKind: ["ui"]`), и в буфер кладётся конфиг с путём к `.exe`,
  который из шелла дистрибутива не запустится. Тег `mcp-v0.1.0` выпущен 2026-08-28, так что кнопка
  уже рабочая — и этот пункт стал актуальным, а не будущим.

  **Но обходной путь есть, и он измерен.** WSL наследует пользовательский PATH Windows (проверено:
  exe из `%LOCALAPPDATA%\Programs\…` резолвится в bash по голому имени), а *Copy install command for
  another machine…* → `creds-mcp` → **Windows** ставит бинарь именно туда и дописывает его в user
  PATH. После этого мост находит `creds-mcp.exe` сам и `CREDS_MCP_WINDOWS_BINARY` не нужен вовсе.
  Кнопка *Install the MCP Server…* кладёт бинарь в хранилище расширения **намеренно не на PATH**, и
  тогда переменная обязательна. Два маршрута с разным следствием — этого не говорит ни один из них.

  Что стоило бы сделать: ветку «агент живёт в WSL» в самой установке — она уже умеет перечислять
  дистрибутивы (`chooseDistros` для релея ssh-агента), так что могла бы поставить Linux-половину
  туда, виндовую на PATH, и положить в буфер конфиг с ПУТЁМ ЛИНУКСОВОГО бинаря.
- **`can.create` у записи и «папка открыта для создания» — не одно и то же.** Найдено при ручной
  проверке: `creds_list` отдаёт записи `can.create: true` (её собственный или унаследованный
  переключатель), а `creatableFolders` требует переключатель на **самой папке**, так что агент
  получает `create: true`, вызывает `creds_create` и получает отказ. Отказ хороший и называет
  переключатель, цена — один потраченный вызов и вводящее в заблуждение поле. Решать — владельцу.
