# PLAN — Синхронизация через приватный git-репозиторий

> Status: **IMPLEMENTED 2026-08-25 (0.58.0).** Отклонения: (1) распознавание git — только по
> однозначной форме (`ssh://`, `git@host:`, `git+`, `.git`), а не по отдельной настройке
> `accountGitRemotes` — существующий `nasBackupPath`/`accountNasPaths` уже несёт локацию, и второй
> ключ был бы лишним; (2) ретенция истории (`gitHistoryDepth`) НЕ реализована — вынесена, потому
> что это перезапись чужой истории и заслуживает отдельного решения владельца; (3) PAT-путь не
> реализован, только SSH-ключ из хранилища плюс наследование настроек машины. **Найдено при
> реализации:** git на Windows переписывает переводы строк при checkout и портил байты хранилища —
> см. §CHANGELOG 0.58.0. Scope: новый `GitTransport` в семье
> `VaultTransport`, трёхсторонний роутинг локации, хранение credential для remote, вызов системного
> `git`. **Решение владельца 2026-08-25: делать полноценно, с историей коммитов бандла** —
> операционная цена принята сознательно (см. §7).

## 1. Симптом и цель

У разработчика Mac на работе и Linux/Windows дома. Чтобы связать их, сейчас нужно либо поднять
сервер (`src_minimasapi_server`), либо настроить общую папку — Syncthing, Dropbox, сетевой диск.
При этом идеальный транспорт для файлов у него уже есть и уже настроен: приватный git-репозиторий.

**Цель:** вставил ссылку на приватный `my-vault-repo` — и обе машины сходятся, без нового сервиса.

## 2. Что переиспользуется целиком — это сильная сторона плана

**Движок синхронизации транспорт-агностичен полностью.** `SyncManager.syncProfile`
(`syncManager.ts:324-448`) обращается к транспорту ровно трижды: `readVault(account)` (`:334`),
чтение флага `embedsShares` (`:370`), `writeVault(account, content, [])` (`:435`). Больше ничего.

А `syncMerge.ts` и `versionVector.ts` **не упоминают транспорт вообще** — `mergeProfiles`
(`syncMerge.ts:139-269`) видит два снапшота и время. Причинное слияние, tombstone'ы, horizon, guard
на фантомы, идемпотентный skip (`syncIdle.ts`) — всё это работает над байтами, и им безразлично,
пришли байты из папки, из HTTPS-GET или из `git show`.

Значит: **`GitTransport` — это один новый класс, реализующий 7 методов интерфейса**
(`vaultTransport.ts:12-58`), и ноль правок в движке.

## 3. Что придётся сделать заново

**Н-1. Роутинг локации — закрытая двоичная развилка.** `isServerLocation`
(`vaultTransport.ts:60-62`) — это `/^https?:\/\//i`, и `TransportFactory.forLocation`
(`transportFactory.ts:48-58`) — тернарник по нему. `kind` — литеральный union `'folder' | 'server'`.
Нужна третья ветка и третий вариант union'а, плюс правило распознавания: `git+https://…`,
`git@host:path.git`, `…/repo.git`, либо явная настройка. **Предложение:** не угадывать по строке
(`https://github.com/me/vault.git` неотличимо от сервера без хвоста `.git`), а завести отдельную
настройку `credSshManager.accountGitRemotes` (email → remote) — и распознавать git по тому, что
локация пришла оттуда, а не по регулярке.

**Н-2. Нет git-клиента и не может быть библиотеки.** У расширения **ноль runtime-зависимостей** —
только Node built-ins и `vscode` API. Значит `simple-git`/`isomorphic-git` исключены, и остаётся
**системный `git`**. Это первый случай, когда расширение потребует внешний инструмент как условие
работы функции (`ssh` и клиенты БД нужны только для действий, которые пользователь сам настроил).
Форма запуска готова: `runBounded('git', argv, false, {env, timeoutMs, signal})`
(`sshExecRunner.ts:85-165`) — те же ceilings, тот же `AbortSignal`, тот же «никогда не `shell:true`».

**Н-3. Запись — это коммит, а не перезапись байтов.** Ни один существующий транспорт не имеет
понятия истории: папка делает temp+rename (`atomicFileWrite.ts:23-38`), сервер — `If-Match`/ETag
(`serverTransport.ts:126-148`). Git-запись — `commit` с автором, сообщением и растущим логом.
Владелец выбрал **полноценную историю**, поэтому:

- одна ветка `creds-vault` (не `main`), файл `vault_<hash>.enc` — по одному на аккаунт, как в папке;
- сообщение коммита **не содержит ничего о содержимом**: `vault: <account-hash-prefix> <ISO-время>`;
  имя записи, число записей и что менялось — это метаданные утечки, в публичном-по-структуре логе им
  места нет;
- автор — настраиваемый, по умолчанию `CredsForDevs <creds@localhost>`, чтобы не подмешивать личность
  разработчика в служебные коммиты;
- **ретенция:** настройка `credSshManager.gitHistoryDepth` (по умолчанию 200 коммитов). Превышение —
  фоновое `git checkout --orphan` + один коммит + force-push, раз в N дней. Это единственный способ
  не дать логу расти бесконечно, и он должен быть в плане с самого начала, а не «когда заметим».

**Н-4. Конкурентность = `git push` rejection.** Прямой аналог `412` у сервера. Контракт копируем с
`serverTransport.ts:134-143`: rejection → сбросить кэш → **не** пытаться повторить тот же push →
следующий цикл прочитает, сольёт причинно и запишет заново. **Никогда `--force`** (кроме
контролируемой ретенции из Н-3, и только когда локальная копия свежее remote).

**Н-5. Credential для remote — новая ось хранения.** Сегодня **ни один** ключ SecretStorage не
привязан к локации: все они `${accountId}_${entityId}[:field]` (`storageManager.ts:41-83`).
Для git нужен либо PAT, либо deploy-ключ. Два варианта, и оба стоит поддержать:

- **SSH-ключ:** переиспользуем `materializePrivateKey` (`keyInstaller.ts:115-127`) — 0600 в уже
  вычищаемый `keys/`, и `GIT_SSH_COMMAND=ssh -i <path> -o IdentitiesOnly=yes`. Ключ берётся из
  **существующей записи хранилища** (`sshkey`) по ссылке — то есть новой оси хранения не нужно
  вообще, нужна только ссылка `gitKeyEntityId` в настройке remote. Это предпочтительный путь.
- **PAT:** новый ключ `git:<sha256(remote)>` в SecretStorage — минимальная новая ось, и только если
  выбран HTTPS-remote. Передаётся через `git credential` helper на stdin, **никогда** в URL
  (URL попадает в `.git/config`, в логи и в `ps`).

## 4. Как выглядит цикл

```
readVault(account):
  ensureClone()                       # git clone --depth 1 --single-branch -b creds-vault, один раз
  git fetch --depth 1 origin creds-vault
  git reset --hard FETCH_HEAD         # рабочая копия — кэш, а не источник правды
  прочитать vault_<hash>.enc или undefined

writeVault(account, content):
  записать файл, git add, git commit -m "vault: <prefix> <iso>"
  git push origin creds-vault
  при rejection → сбросить кэш, НЕ повторять; следующий цикл сольёт
```

Клон живёт в `<globalStorage>/git/<sha256(remote)>/` — приватный каталог расширения, тот же, где
уже лежат материализованные ключи, с той же уборкой.

**`embedsShares = true`** — как у папки: shares едут внутри конверта, отдельного инбокса у git нет.
`appendShares`/`removeShare` копируют оптимистичный retry-and-verify из `folderTransport.ts:116-160`,
но на уровне «push отклонён → перечитать → повторить», максимум 3 попытки.

## 5. Операционная цена, принятая владельцем

Честно, чтобы это было видно до реализации, а не после:

- Авто-синк дебаунсится 5 с после правки и идёт по таймеру (`autoSyncIntervalMinutes`, по умолчанию
  5 мин). Каждый цикл — это `git fetch`. **Против хостинга** это сетевой вызов каждые пять минут на
  каждую машину; у GitHub есть лимиты на API, но `fetch` по git-протоколу их не расходует так, как
  REST — тем не менее замер нужен (§8).
- **Требование:** `git` на PATH. Отсутствие — это не молчаливая деградация, а внятное сообщение с
  указанием, что установить (по образцу `tool_missing` в брокере).
- Первый `clone` может быть заметно долгим на медленной сети — прогресс через
  `withProgress`, и **никогда** на UI-потоке (у нас и так всё через `runBounded`).
- Растущая история — решается ретенцией Н-3, но это фоновая перезапись истории, о которой
  пользователь должен знать заранее (документация + настройка).

## 6. Порядок сборки

1. `gitRemote.ts` (чистый): разбор/нормализация remote, выбор ssh-vs-https, построение argv для
   `clone`/`fetch`/`commit`/`push`, разбор кодов и stderr git'а в понятные ошибки. **Тесты — здесь**,
   без сети.
2. `GitTransport` над `runBounded` + `gitRemote`; `kind: 'git'`; `embedsShares = true`.
3. Роутинг: настройка `accountGitRemotes`, третья ветка в `TransportFactory`, расширение union'а.
4. Credential: путь через существующую `sshkey`-запись (`GIT_SSH_COMMAND`); PAT — вторым шагом.
5. Rejection-контракт + тесты на «push отклонён → следующий цикл сходится».
6. Ретенция истории (`gitHistoryDepth`) + фоновая перезапись.
7. Интеграционный тест против **локального bare-репозитория** (`git init --bare` в temp) — сеть не
   нужна, а весь путь clone/fetch/commit/push/rejection проверяется по-настоящему.
8. Документация: README (третий транспорт), `module_extension.md`, `architecture.md` (диаграмма
   транспортов), предупреждение про `git` на PATH и про перезапись истории.

## 7. План тестирования

- `gitRemote.ts`: разбор ssh/https/scp-подобных remote; argv не содержит секрета; PAT никогда не
  попадает в URL (явный тест).
- Против локального bare-репо: первый clone → запись → чтение с «второй машины» (второй клон) →
  причинное слияние двух правок → **rejection** (в bare коммитит третий) → сходимость на следующем
  цикле.
- Отсутствие `git` на PATH → внятная ошибка, синк не «тихо не работает».
- Ретенция: после N+1 коммитов история усечена до N, содержимое последнего состояния идентично.
- Сообщение коммита не содержит имён записей и их числа (тест на регулярку).
- Замер: длительность `fetch` на пустом цикле, и число сетевых вызовов за час при активной правке —
  в CHANGELOG.
- `syncMerge`/`versionVector`/`syncIdle` — **ни одного изменения**; их существующие тесты должны
  остаться зелёными без правок (это и есть доказательство транспорт-агностичности).

## 8. Definition of Done

- [ ] `GitTransport` реализует все 7 методов; движок синхронизации не изменён ни на строку.
- [ ] Интеграционный тест против локального bare-репо покрывает clone/read/write/rejection/сходимость.
- [ ] Секрет (PAT) не появляется ни в URL, ни в argv, ни в `.git/config`.
- [ ] Сообщения коммитов не раскрывают содержимое хранилища.
- [ ] Ретенция истории реализована и настраиваема; поведение задокументировано до того, как кто-то
      увидит force-push в своём репозитории.
- [ ] Отсутствие `git` — явная ошибка с инструкцией.
- [ ] README/`module_extension.md`/`architecture.md` описывают три транспорта и когда какой выбирать.

## 9. Что стоит сказать вслух

Серверный транспорт уже даёт офф-сайт и историю, проще и без взаимодействия «git-merge против
причинного merge». Git выигрывает в одном: **у разработчика уже есть приватный репозиторий и не
нужно ничего поднимать**. Это настоящая причина, и владелец выбрал её сознательно — поэтому план
делает полноценную версию, но фиксирует цену (внешний `git`, сетевой вызов каждые 5 минут, фоновая
перезапись истории) в документации, а не в разделе «известные проблемы» после релиза.
