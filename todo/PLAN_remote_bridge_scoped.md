## Reading this plan: contracts, sketches and observations

Three kinds of line stand in this document, and a reader must tell which is which before building against one or correcting one. The re-review for epoch 5, after the plan's third stop, read the drift as being in what the plan treated as authoritative, not in the epic split: a release-note sentence prescribed in two places was read as a contract and was false (change 4.2), and an implementation sketch (D.8's order) was built as written where its contract, *every request is answered and the journal is bounded*, was what mattered (change 4.3).

- **Contracts** are what a coder builds against and a test pins: the owner's decisions of §2 and the decided rows of §2.1; §4.2's allow-list, never-list and the named field list of a served read; §4.6's run-site table; §4.7's five-clause predicate, the hold's rules and the five-step order of a lock's close; §4.9's table, file shape and cost list; §4.10's table and its *Accepted*; §4.11's bridged flags; §4.1's journal bound; §4.3's note schema; §4.5's one answer for an expired token; the merge conditions of Q7, §5 step 3 and E1's PR shape; §9 whole; each epic's *Done when*. **The list is not closed:** a line is a contract by what it does (a coder builds against it, a test pins it), not by appearing here, and a line that lacks a file, line or date is no less one; whether changing it counts is decided by the rule's own list, never by this one. A contract line is expected to name the file and line it was walked against, and the date. **A sentence about one action's behaviour is a contract, whether or not a test pins it yet**: what an action asks after its Allow, what it keeps, what it answers. A sentence with no test is owed a test, not downgraded to an observation; it is written together with the test wherever that is possible and never from reading alone. Change 5.2 stopped the plan on `down keeps nothing`, a sentence three reviews had read and none had tested; the audit for epoch 6 then found two more actions on the wrong side of the same sentence (`rotate`, and `exec` on a forwarding entry), and the fourth stop is the one that reads like a pattern. The per-action facts live in §4.10's contract paragraph; the audit that is their evidence stands beneath it as an observation, and the two are not one paragraph. **And a test of the words is not a test of the claim** (change 6.2): an exact-string assertion preserves a false sentence perfectly, so a sentence about where something runs or who receives data is pinned only by a test that also observes the execution or the recipient it names (what was spawned, where, with which connection; what went back and to whom), beside the words.
- **Sketches** say how a contract is expected to be met: a module name (`consentPlace.ts`, `bridgedSshConfig.ts`), a function's shape, a line count, where a limiter sits, the order of two statements. A sketch that proves wrong is replaced in the story's spec, which says why; whether that replacement is an entry is the rule's question (`approach` counts there), never this paragraph's.
- **Observations** record what was read or measured, with its date and commit: §1's cause tables, §2.2, §4.11's measurements, §7's M rows, and §4.10's lists of what partial E1 changed on the local doors. An observation written from reading says so; one a measurement could settle is named in §7's M table or in its own row. A release note (`CHANGELOG.md`) is an observation about the diff at the commit that writes it: derived from that diff, checked line by line against it, and never prescribed here or in a spec verbatim. **An observation can carry a condition:** §4.10's second list is what §7's *Local doors at partial E1* and §5 step 3 require evidence for, so dropping a row from it, or moving a row to the third list, makes a merge condition smaller: that is a narrowing, it counts, and the owner approves it first.

**What this classification does not do.** It does not decide what counts as a change. That is `plan-change-control.md`'s list, which outranks this plan, and in doubt it is a change. Inside that rule's "a fix that only satisfies the plan as written", this plan reads itself narrowly: a correction to code is outside the count only when it names the contract line above that it restores, carries a regression test that shows the restored behaviour, and changes no approved behaviour, scope, dependency or risk; a correction that cannot name its contract, or whose reader is in doubt, is an entry. Nothing here lowers a count already written, and nothing here is a reason to leave an entry unwritten.

## 2. Owner decisions (2026-11-04)

1. Finish the bridge AND scope it per server. `ssh -R` is the transport.
2. No plaintext secret reaches the server. A password is used without being seen: the laptop runs a stored command with
   the password in a variable, and the agent gets only the output. (Amended by the owner with two named exceptions, 2026-11-05 and 2026-11-06: below.)
3. No open window means no access: no daemon and no relay. Calls fail with a clear message.
4. **Bridges survive a reboot of the person's PC.** A bridge stays open until the person closes it. Closing a window suspends it;
   only *Close Remote Bridge* ends it.
5. The person's own `Set env` keeps working in a Remote-SSH window, with a warning. Only an agent's export is refused.
6. Script entries are usable by the agent when access is open. The VPN is one such script (`vpn-up`, bash, on the server), it serves
   websites, not databases, and it does not prompt for a sudo password; the plan does not handle one.
7. Each login user has its own entry and bridge. The owner's Remote-SSH window logs in as a non-root login, so an agent there needs an entry
   for that login; a root entry's private directory cannot serve it. (The real host name and login were in this plan until the third pass; this repository is public, and they are not written again. No history rewrite.)
8. Out of scope: RDP, and any tunnel to a database. Databases are queried from the laptop as today.

**Decision 2, as the owner decided it on 2026-11-05 (the revision for epoch 4 asked; this answer changes the decision, by one named exception).** Nothing in plaintext reaches the server, with two exceptions the owner accepts, this one and the next paragraph's: a password entry whose destination is that server itself. There the password reaches that server's `sshd`, because that is what password login is, and an agent there running as root can read it; the person is told so plainly when choosing what the server may use (§2.1 Q4). Read as three recipients: the **bridge server**, where the agent runs, receives no credential in any form, except as the destination of such an entry. A **hop** of the entry's typed jump chain receives a signature made with that hop entry's own key, and the destination's address and port in `-W` (that is what a hop is for), and nothing else. The **destination** receives what authenticates to it: a signature, or, for a password entry, its own password in plaintext; it is sent only to a destination whose host key the entry pins (§2.1 Q3). The exception covers the tunnel as well as an exec: the `ssh -R` of E2.2 logs in to the bridge's own entry (`commands/agentCommands.ts:437-450` resolves the same credential as an exec), and an unattended reconnect (§4.7) sends the password again with no dialog. §4.9 is the whole table.

**A second accepted case, the owner's decision of 2026-11-06 (§2.1 Q10, confirmed and widened).** Any stored line or body that runs on the server goes there as written: a script entry's body, and a Terminal entry's `command` with its `commandArgs` (`agentUseActions.ts:202` builds the line from both, `runPlan.ts:76-78` reads both as the texts to check). A literal password or token typed into any of them crosses with it, and the agent on that server reads it as it runs it; nothing can tell a literal from any other string, so no guard is promised (§4.6). A value by `creds://` reference does **not** cross, because a line with a reference runs on the laptop (§4.6 rows 3 and 4) and only its output goes back. So decision 2 has two exceptions, Q4's and this one; the scope pick says on every Terminal and script row: *write secrets through `creds://` references; when it runs on the server, anything typed into the text is seen by the agent there*; a test pins the sentence; §9's secret line carves the case out. It follows from decision 6: `vpn-up` is a script that runs on the server, and a body that does not cross cannot run there. **D12 and this case are not in contradiction, stated so nobody reads them as one:** D12 drops `command` from the served *listing* because of what the text holds (a `creds://` reference naming an account and an out-of-scope entry, or a literal) and a listing is a read with no consent; *running* the line on the server still sends the text, under a consent and inside the scope the person chose. The text does not cross when the agent looks; it crosses when the person has let the agent run it there.

## 4. Design

### 4.1 One listener per open bridge, behind a third door

`ssh -R` from Windows can only target a TCP port (`sshBridge.ts:12-17`), so each open bridge gets its own
`startLoopbackServer()` port, closed with the bridge and on `dispose`. `doorsFor` (`brokerOrigin.ts:75-92`) mints a third
door, `forBridge(port, context)`, so "every listener is covered" stays structural. The door keeps the browser-header
checks and the exact Host rule, and additionally requires an `X-Creds-Bridge` key with a constant-time compare.

The key exists because any local Windows process can reach that port, and without it such a process could raise a modal
claiming to come from this server, or borrow a quiet scope. It is minted per open, dies with the listener, and opens no
secret. It does sit on the server (§4.3), readable by that unix user, who can reach the socket anyway.

The door hands a trusted `BridgeContext` `{bridgeId, accountId, serverEntityId, serverName, target, remoteOs}`, the key staying at the door, to
`handle`. Nothing in a request can set or change it. `credsAgentServer.ts` is at 789 of 800 lines (at `541d709`; the record's 788 is historical), so new behaviour goes in
new modules (`brokerBridgeListeners.ts`, `bridgeContext.ts`).

**Failures before any route, and their logging budget** (D21; the bound is a contract, the limiter's place a sketch). A throw out of `handle` is answered 500 with the generic sentence and nothing of the error in the body, by `unanswered` at the one `.catch` the three doors share (`credsAgentServer.ts:697`; D.8 of the E1.3 spec's Amendment 4, built in `88befcd`, its order fixed in `a04ca33`: answer first, then the line inside a `try`). Every request is still answered: a budget bounds the journal, never the answer. **The line carries no raw text of the error** (the re-review for epoch 6, 2026-11-06; a contract). At `fdcc55a` `unanswered` writes `describeError(error)` into the line (`brokerRequests.ts:318`), and a Node `JSON.parse` message quotes its input, so which strings reach the journal is unknown. The line is a fixed classification instead: the error's class name when it is a built-in (`Error`, `TypeError`, `RangeError`, `SyntaxError`, `URIError`, `ReferenceError`, `EvalError`, `AggregateError`; anything else reads `Error`); a Node `code` only when it matches a strict shape (`^[A-Z][A-Z0-9_]{1,40}$`); the name of the route the request matched in `BRIDGE_ROUTES` alone, `other` for anything else (a real route outside that table, such as an alias action, must not read as "no route"; the raw path never), handed to `unanswered` as an argument because `brokerRequests → bridgeAllowList → bridgeScope → brokerRequests` would be an import cycle; and whether the headers had already gone out, read from `res.headersSent` **before** `respondError` runs. **The body's sentence changes with it:** `INTERNAL_FAILURE` promises "See the agent journal for the reason", which `unanswered` can no longer keep; `unanswered` answers its own sentence, that the request failed inside the window and the journal records that it failed and where, while `INTERNAL_FAILURE` stays for the handlers that do journal a reason. On E1.4's tree the line also carries `auditGrantMark`, beside the classification. Never `message`, never a stack, never a path, header or body. Where this plan says *the reason goes to the journal* of a handler failure, it means this classification. The notes that carry `describeError` text today (`sshUseActions.ts:214`, `credsAgentServer.ts:413`) are a §8 todo, not this plan's change; §7 has the sentinel case. The line it writes is **bounded per door**: at most one line per door per minute for handler failures, the one-report-per-window shape `firstThisWindow` already gives the asking ceiling's refusals (`aliasThrottle.ts:453-459`; it answers a boolean and keeps no count, so the count of suppressed failures that the next line written carries is new state beside `reportedAt`); a bridge door is its own door, the local doors share theirs. Where the limiter sits is the spec writer's (beside `DoorCounts` in `aliasThrottle.ts`, or in a module of its own if that file is squeezed); `unanswered` takes it as an argument, so a test can see it. **It is a condition before a bridge door is live:** E2.2b builds it in the commit that removes R1, and §7's case runs 200 requests against a supplier that rejects, through E2's forwarded listener, because bridge reads run before any admission and the key-holder's rate is bounded by nothing else. At partial E1 the catch path exists on the local doors too, reached only by a handler that throws, which no caller has been shown to induce (the one induced throw, `GET //`, is answered with no line since `a04ca33`, §4.2): the limiter is not required of the partial-E1 merge, and §6 names the surface.

### 4.2 Scope at the lookups, not the listings

`bridgeScope.ts` (pure) wraps the resolvers (`resolveMcpUse`, `resolveAlias`, the token's grant) and the read sources for a
bridge door, so a direct call with a known id meets the same wall as the list. Out of scope answers exactly like "not
found".

- **Stored:** one file per record, `<globalStorageUri>/bridges/scopes/<hash>.json`, machine-local and never in the vault (the argument of `mcpConsentPolicy.ts:13-18`), named by a hash of account and server entry because the key's characters
  are not legal in a Windows file name. Not `globalState`: each window holds its own copy and the last write wins (`mcpConsentPolicy.ts:234-241`), so a scope narrowed in one window might never reach the window that owns the bridge, and a stale
  write could restore it. Every check reads the file fresh; an absent or corrupt file is an empty scope.
- **Retired with the bridge:** *Close Remote Bridge* removes the scope record and that server's consent stamps along with the bridge's record, whichever window it runs in. Opening the bridge again starts from an empty pick.
- **Written safely:** a record carries a revision. A write takes the cross-window lock of `leasedQueue.ts`, re-reads, and is refused if its revision is stale, so an edit made from an old copy cannot restore what another window removed, and the person is told to look again. The write itself is temp-and-rename. **Only ENOENT means absent** (the re-review for epoch 6, 2026-11-06; verified by reading): `nodeScopeFs.readSync` answers `undefined` on any error (`bridgeScopeStore.ts:222-228`) and public `read` turns that into `NO_SCOPE`, which fails closed for a check; but `set` re-reads through that same `read` (`:159`), so an EACCES or EIO would read as an absent file and `set` would write a fresh record with a new revision over one it could not read. `set` therefore reads through a path that tells ENOENT from every other error and refuses on any other with zero writes, while public `read` keeps failing closed to `NO_SCOPE`. It only satisfies the sentence before it (nothing is written over a record that was not read); §7 has the case. **Shape, decided (the re-review for epoch 6):** the strict read is used by `set` alone; public `read` keeps its catch and `NO_SCOPE`; `prune` (`bridgeScopeStore.ts:190`) stays tolerant and **skips** a neighbour it cannot read instead of ranking it first for removal (today an unreadable file scores `at 0` and goes first); and a file that exists but does not parse as this account's and server's scope record, a foreign or corrupt one, is **refused by `set` too**, with zero writes, since `read` answers `NO_SCOPE` for it and an overwrite would be a write over a record that was not read; the person is told to look again, and *Close* (`forget`) is the road that removes such a file.
- **Chosen:** when opening the bridge, from that account's entries already open to MCP (the same wall as the MCP listing), and editable on the bridged row. A new server starts empty. The pick names the key each ssh entry uses (below).
- **The bridge door serves an allow-list, default deny.** A route or action added later is refused here until it is named. Never on
  the list: `/v1/config/read`, `exportEnv`, `/v1/mcp/create`, `/v1/mcp/folder/*`.
- **An unparseable request target is a path no route matches** (change 4.3): `requestUrl` (`brokerRequests.ts:270-284`) reads a target `new URL` cannot parse against `http://127.0.0.1` as `/unparseable-request-target`, so a bridge answers `not_supported` and the main port `not_found`, with no journal line, before any route or throttle; a test sends 200 of them to both doors (`bridgeKeptPlace.test.ts:383`). Measured (2026-11-06, Node): `//`, `///`, `http://[` and `/\` throw and take the fallback; a bare host does **not**: `example.com` parses as the path `/example.com` and `example.com:80` as a URL of scheme `example.com:`, so each is an unknown route on its own, and the comment at `brokerRequests.ts:270` ("a bare host") is wrong and is corrected in the fix-forward. D.8's "500 on a throw" was never meant for a client's bad target, and the only line a throw may write is §4.1's bounded one.
- **What a served read returns is a named field list, default deny** (D12; built in the partial-E1 closing commit, with the scope wall it belongs to, and asserted by E2.2 before R1 goes). `narrowed()` stops spreading the stored row and builds the bridge's row field by field; a field not named here is dropped, and a test walks every field of every row type of every served read route against this list. `GET /v1/mcp/entries`, per row: `id`, `name`, `kind`, `folder` **served as `''`** (the client's `Folder` is non-null, `McpJsonContext.cs:54`; `folderNameOf` gives the inherited folder's name, `mcpEntries.ts:283`, and a folder is in no scope, so the name would be the one out-of-scope word still served), `host`, `port`, `user`, `dbType`, `vpnType`, `scriptLanguage`, `hasPassword`, `hasPrivateKey`, `hasNotes`, `hasTotp`, `codeAccessEnabled`, `dependsOn` (names in the scope only), `can` with its four keys, `use` as resolved and `edit`, `create`, `delete` false (`bridgeScope.ts:121-127` builds it so; the client's record has four keys, `McpJsonContext.cs:69-73`). Dropped: `connectionString`, replaced by `hasConnectionString: boolean` (`withoutPassword` strips one dialect of four, and the string is the secret); `command`, replaced by `hasCommand: boolean` (a command carries `creds://` references that name an account and an out-of-scope entry, or a literal; the agent runs a line by id and needs no text; running it on the server still sends the text, §2 Q10). The test's cases: a key-value password (`Password=…`), a query-string password (`?password=`), a password holding `@` or `/`, a command with a reference to an entry outside the scope, and an entry inside a folder (`folder` is `''`). `GET /v1/aliases`, per row: `name`, `kind` (`AliasListEntry`, nothing else exists). `GET /v1/mcp/config-snippet`: `envVar`, `languages`, `snippet` (public text from the file name and format, `mcpSnippetRoute.ts`; the body is never served), `error`. `GET /v1/mcp/folders`: an empty list. `/v1/health`, `/v1/mcp/kinds`, `/v1/mcp/kind-help`: the product's own text, no vault data; `KindHelp` and `KindRefusal` (`brokerReadRoutes.ts:89-105`) have no field list of their own, so the test asserts those routes' bodies **byte-equal between an empty vault and a full one**. `POST …/exec`: `exitCode`, `stdout`, `stderr`, `stdoutTruncated`, `stderrTruncated`, `timedOut`, `durationMs` (`sshExecRunner.ts:193-201`): the agent's own command's output, masked by the call's mask table (§4.6). `POST …/query`: the rows the **agent's** SQL returned to the laptop. The SQL is the agent's, not the person's (`agentUseActions.ts:342`, `String(body.query)`), and under `quiet` with `never` nobody reads it; so the pick says on a `query` row that *the agent writes the query, with everything this login may read or change, and the result goes to the server*. What the laptop's database client may do under agent-written input is §4.11. **The local MCP door serves `connectionString` and `command` as today** (the same builder, `mcpEntries.ts:150,180`): a stored MSSQL password crosses to a local agent there with no bridge; that is a todo of §8, not this plan's change, and the allow-list refuses nothing locally.
- **Checked again just before launch.** Name resolution is one wall; a token's grant skips it, and a scope can change while a consent
  modal is open. So the scope is also checked in one place at the moment an action starts, whichever route it came by, and before anything an Allow triggers (`releaseWaiting`, `credsAgentServer.ts:586`), so a narrow during a modal promotes nothing. A token denied while its call waits is refused at that point too. **And a token that is gone** (the re-review for epoch 6; E2.2b): `launchGate` (`bridgeScope.ts:350-356`) reads `grants.get(spend)?.status === 'denied'`, so a bridged token call whose token expired or was evicted while the dialog stood passes the gate and `releaseWaiting` runs (`credsAgentServer.ts:573-577`): a waiting rotation is released for a token that is gone. The action itself does not start: `brokerCall.ts:144` refuses the reservation before `startNow`, so "zero action starts" is true today and the release is the whole harm. Reading `undefined` as a refusal is not enough either: `get` applies no expiry (a probe reads `get` allowed, `lookup` expired, `get` undefined), so the gate reads the token through `tokenStatusNow`, refuses on `undefined` or `denied`, and returns the refusal itself (code and sentence, D22's *Unknown*), which `launchRefusal`'s boolean cannot carry. Unreachable before E2 (R1); a condition before a bridge door is live, built in E2.2b's R1-removal commit with §7's case. The gap between the start of `run` and the spawn is a keychain read and is accepted.
- **References are scoped too.** Every entry a stored command or script reaches through a `creds://` reference must be in the same server's
  scope, or the call is refused with one sentence that echoes nothing from the stored text. Otherwise an entry in scope becomes a road to one that is not.
- **Listings are per account.** `McpEntry` carries no account and an envelope may repeat an id across accounts (`idQuarantine.ts:41` keeps a safe id), so walling by id alone is a breach: the wall reads the listing and the config snippet from per-account suppliers. Use paths already search one account (`mcpHooks.ts` `accountOnly`).
- **What an entry links to is part of using it.** An ssh entry's `sshKeyEntityId` and jump chain are not scope targets. `sshkey` can never be opened to MCP (`entityKind.ts:155,179`), so requiring it would refuse every ssh entry with a linked key. The value stays on the laptop, the person set the link, and edit verbs are off the allow-list, so an agent cannot repoint it. This covers what using the key does, including promoting a rotation already waiting on it (`automaticRead.ts:28-33`). A `creds://` reference stays strictly scoped, because it puts a value into a command.
- **But never the laptop's whole agent:** `agentForward` forwards the shared agent, which lists every loaded identity (`sshUseActions.ts:83-97`, `sshAgentServer.ts:207-208`). An ssh entry with it set is refused on a bridge door, with a sentence saying why, until forwarding has its own boundary. Nor any other forwarding, and no shared connection (change 3.1): on a bridge the entry's port forwards are dropped from the composed argv and `ssh` is told `ClearAllForwardings=yes`, `ForwardX11=no`, `Tunnel=no`, `ControlPath=none` and `ControlMaster=no` — one fresh connection that carries the command and nothing else, so an exec cannot join the person's own multiplexed session (which would hand it the forwarded agent and skip the pinned key and host key) or open a road from the server through the laptop; off a bridge the argv is unchanged. Since the revision for epoch 4, everything a bridged `ssh` may carry, receive and run, leg by leg, is §4.9; this bullet is the scope-side half of it.
- **Refusals name nothing out of scope.** On a bridge door the sentences that carry a linked entry's or jump host's name (`sshExecAuth.ts:125-127`, `sshOptions.ts:153`) become generic. `ssh`'s own stderr is returned as is, and may carry a jump host's address, or the laptop's key path and a linked key's id in the file name of a key `ssh` could not load.
- **Server identity is the vault entry id** (`serverEntityId`), never a host string, so aliases and jump chains cannot split or merge it.
- **Prompts:** each bridge has its own sliding window of prompts, so one server's agent cannot spend the laptop's or another server's, while one dialog at a time stays the window's (§4.10: the place is per VS Code window, never global). A call the gate refuses before any dialog spends no prompt. Who owns that one dialog place from admission to recovery, and what a timer may and may not do to it, is §4.10.
- **"Never ask" and "every 12 hours":** a per-server `quiet` switch, default off, which means every call through this bridge
  asks. When on, the entry's own policy applies, with stamps keyed by server too, so an answer given through server A
  silences neither server B nor local use. `stampKey` keeps its length-prefixed encoding with a third segment, so a local stamp and a
  server stamp cannot collide.
- **Modal and journal:** one added line from the context, not from the caller's self-declared label: which server, and
  where the action runs, true per action, because the modal is the authorisation: for `exec`, *The connection starts on this computer; the command runs on "<entry>", and its output goes back to that server.* (a statement of the initial destination: kept, and not strengthened to "only its output", because Q4 lets the bridge's own entry authenticate to the bridge server itself, so more than output can reach it); for `query`, since the revision for epoch 7 (change 6.2), *The database client runs on this computer, using the connection stored in "<entry>". Its output goes back to the agent on that server.*, because only the client runs here (`runBounded` spawns it locally, `agentUseActions.ts:372`) while the SQL runs on the database the stored connection names (postgres gets the stored URI, `dbCliLauncher.ts:271`; mysql parsed flags with `-h` defaulting to `localhost`, `:275`; sqlcmd `-S` and an optional `-d`, `:296`), and the sentence names neither "the database the entry names", which mysql's `use` and sqlcmd's context switch can leave behind, nor "only its output", which is false when the database stands on the bridge server itself; for E3's `run`, the sentence is **chosen from each `decideRunSite` result, never from the action's name**: *It runs on that server.* for the server rows of §4.6's table alone, the laptop sentence for the Windows rows, and no dialog at all for a refused row, which is refused before any dialog. Audit lines gain `bridge=<name>`.

### 4.3 A stable note, not a stable socket

A stable socket path has a trap: after a laptop sleeps, the old `sshd` session can keep the path bound with no client-alive
check, so a reconnect either fails on `ExitOnForwardFailure` or has to unlink a socket that might be another window's
live one. So the **socket path stays per connection**, and the stable thing is a **note**:

- Directory: `~/.creds-for-devs/bridge/`, mode 0700. The 0700 parent is the first layer; sshd's mask (which the client
  cannot set, `sshBridge.ts:19-24`) is the second, still checked by `verifyBridgeSocket`. **`-R` takes an absolute path** (today's is `/tmp/creds-<user>-<id>.sock`, `sshBridge.ts:68`), so the first `ssh` of every connection is a home-discovery exec (`printf %s "$HOME"`) under §4.9, and the directory is created and the sweep run by a second one before the tunnel is spawned; a home that is not an absolute path, or holds a character outside `[A-Za-z0-9._/-]`, refuses the connection with a sentence.
- **Every live bridge has its own note**, `<bridgeId>.json`. An entry has one bridge per laptop: a second Open from another window finds the existing one (§4.7). Different logins are different entries, so different bridges with their own notes and scopes, and each writes and removes only its own note. A second laptop has its own `bridgeId`.
- Each connection: unlink every earlier socket of this `bridgeId`, listening or not, because the supervisor knows they are superseded and
  clients follow the note; then sweep other sockets, removing one only when `ss -lx` ran successfully and does not list it as listening. If `ss` is missing or fails, the other sockets are left alone, because nothing has proven them dead; spawn `ssh -R <dir>/<bridgeId>-<attempt>.sock:127.0.0.1:<bridgePort>`, where `<attempt>` is a random id minted for this connection attempt, not a counter: the record is never rewritten and the pipe holds no data, so a counter has no store across a handover (§4.7);
  verify the socket; and only then atomically write the note (mode 0600): `{socket, port, brokerPort, key, serverName, attempt, openedAt}`. **The note travels over stdin** of a bridged exec (`umask 077 && cat > <tmp> && mv <tmp> <note>`, so the file is 0600 from its first byte whatever the login's umask), never as an argv operand: the door key and `serverName` (vault text) would otherwise stand in `ps` and in a shell line. The bounded stdin path of `sshExecRunner.ts` (end-of-file, write error) is therefore E2.2's, not E3.2's, and E3.2 reuses it.
- A note whose socket is gone is removed by the same sweep, whoever wrote it.
- **Each attempt owns its generation** of socket and note; the listener and key live as long as the open bridge. A superseded attempt can neither publish nor delete a newer note
  (the identity check `sshBridgeManager.ts` already makes for a late exit, extended to verify, publish, retry and clean up). Within one owner the generation is the attempt id in memory. **Across a handover** nothing carries it: the old owner has either died (the OS released the pipe; none of its work can still run) or locked (it closes tunnel and listener and cancels its waits *before* releasing the pipe, §4.7), so no straggler of a previous owner can publish; the random attempt id makes any note that nonetheless appears attributable, and the sweep removes a note whose socket is dead whoever wrote it. No compare on the server is needed, and none is made.
- Close removes the note, best effort, and cancels any waiting retry. A stale note is harmless: its socket is dead and its key died
  with the listener.
- A path over the socket limit is refused with a sentence, using the limit of `src_cli/src/AgentRelay.cs:116-119`, moved to `src_broker_client` so both clients share it.
- So without `ss`, a bridge still unlinks its own earlier sockets; only other bridges' dead sockets stay, at most one per bridge ever
  opened, and this is said once (§6).

A connection belongs to the login user of the entry. A bridge opened on a root entry serves agents running as root; an
agent running as another user needs an entry for that login, which is another bridge.

### 4.4 The supervisor

`BridgeSupervisor` (pure, spawner and clock injected) replaces `SshBridgeManager`: `connecting → up → down(retry) → closed`,
backoff 2 to 60 s with jitter, until Close; it is suspended when the window ends (§4.7). A row reads `up` only after `verifyBridgeSocket` (a local function at `commands/agentCommands.ts:208`, extracted for this) succeeds, never
because a process is alive (the class of defect `sshBridge.ts:95-101` records). The host key and jump chain come from the exec
path's existing code (`materializeKnownHosts`, `resolveJumpChain`), and `bridgeAuthParity.test.ts` extends to the new execs. **Every `ssh` the supervisor spawns is a bridged `ssh` under §4.9**: the tunnel, the home discovery, the directory and sweep exec, `verifyBridgeSocket`, the note's publish and removal, and the version check of §4.5. Today `verifyBridgeSocket` and `sweepDeadSockets` call `buildSshExecArgv(entity, keyPath, cmd, auth)` with no `-F` and the person's environment (`commands/agentCommands.ts:195-225`); extracted does not mean contained, so E2.2 routes them through the one bridged spawner, and a test asserts that every `spawn` the supervisor makes carries `-F` and exactly the allow-listed environment.

**Nothing is ever replayed.** The supervisor owns only the tunnel. A call in flight when the tunnel dies answers "may or may not
have run" (the sentence of `Program.cs:235`), for `creds` and `creds-mcp` alike.

### 4.5 Clients find the note

`BridgeNote.cs` in `src_broker_client` lists the notes and keeps those whose socket exists. **Each live note is one endpoint** in the rung
`Endpoints` gains for when announcements are empty, so the walk that already serves several windows decides (`Windows.cs:104-119`): reads
merge, and a use call moves on from a `not_found`. That is how an entry scoped to an older bridge stays reachable while a newer bridge exists. `BrokerClient` sends the key and the note's port, so Host is right and D2 goes away. **A note is one
snapshot per logical call:** the health probe and the POST use the same socket, port and key, so old and new bridge state never mix.
`CREDS_BROKER_SOCKET` stays as an override that names a socket: key and port still come from the note for that socket. A socket that exists with no note
behaves as today, which keeps `creds-cli-itest.cjs` and the local socket door unchanged. A socket that does not exist gets a sentence: the variable points at a
bridge that no longer exists, unset it. The note is read **per call**, so a running `creds-mcp` and old tmux panes follow a
reconnect with nothing to re-export. A dead socket fails on the existing 2 s health timeout and the next note is tried.

**Token calls must change too.** `CallWithTokenAsync` (`Program.cs:132-156`) dials `token.Port`, which is the main broker's port,
and the bridge door requires its own. A token belongs to one window, so the client picks the note whose `brokerPort` equals `token.Port`, uses
that note's socket, port and key, and sends the token as today. **One answer for an expired token on a bridge** (D22; E2.2b): whichever moment the expiry is seen, at the header by `lookup` or after the body by `tokenStatusNow`, the bridge answers one code and one sentence: **`unauthorized`, *Unknown or missing grant token.*, with no journal line**, the generic answer. Decided here and not left to the spec, because only that answer is possible at all three moments as the code stands: `lookup` deletes the expired grant at the header (`grantRegistry.ts:195-198`), so the call after it cannot name an expiry without new state, and `tokenStatusNow` already answers *Unknown* after the body; naming the expiry would need the bridge to keep what the registry dropped, which is a new store and an entry. It is also what the comment at `brokerBridgeToken.ts:9` meant and what S5 needs (an out-of-scope token, live or expired, reads as a made-up one at every moment). E2.2b makes the header-time path of `bridgedToken` (`bridgeScope.ts:211`) answer *Unknown* for an expired in-scope token too, with §7's case, and the two later moments with it: the launch gate (§4.2) and the reservation at the action boundary (`reservationRefused`, `brokerCall.ts:175-178`, which names the expiry today), so a spent token reads *Unknown* on a bridge at every one of the four moments; at `a04ca33` the two moments disagree, which no production door can show before E2.

**Compatibility:** an old `creds` against the new door is refused, because it has no key and the wrong port, and it cannot even say why: `IsOurBrokerAsync` (`BrokerClient.cs:96-105`) discards a refused health probe, so it reports that no window is listening. Extension tags also go out for unrelated work (`release.yml:809`), so ordering this plan's releases is not enough. So:

- **The new open flow and restore stay behind a switch**, off in every build until E4 flips it after the clients are released. Until then *Open Remote Bridge* behaves as it does today, and CI turns the switch on. The switch is a constant in its own module (`bridgeFlowSwitch.ts`, `BRIDGE_FLOW_ENABLED = false`), and a test owns it from E2.2 on: the packaged default reads `false` and `package.json` declares no `activationEvents` (D19: the manifest cannot sit behind a constant, so the test holds both) until E4.1's commit flips the constant, adds the manifest line and flips that test with them. CI turns it on through the test world and the itest's injected deps, never by editing the constant, so a green CI says nothing about the shipped default. After E2.2 removes R1 the switch is the only thing between a released extension and the new door, and the test is what says so.
- **Clients ship first** (`cli-v*`, `mcp-v*`). Released is not installed, so before the new flow opens on a host it checks that host's `creds` and `creds-mcp` versions and offers the update, instead of relying on a refusal the old client cannot show.
- **E2.1 tests the previously released `creds` against the new listener and asserts its real output** (the sentence it prints when the probe is refused and it reports that no window is listening), as a §7 case; E4.1's version check is then specified against a measured output, not a predicted one. Owned by E2.1 because that is where the note contract is frozen; E4 only re-runs it against the tagged client.

Install: `install.sh` gains a product switch (asset name `creds-mcp-$VERSION-$RID`, `release.yml:687`), the host menu offers
`creds`, `creds-mcp` or both, and registration stays offered rather than written (`mcpClientConfig.ts:9-13`): the person is
shown `claude mcp add --scope user creds -- <path>/creds-mcp` to run on the server.

### 4.6 Where a stored command runs

The bridge door decides, through a pure `decideRunSite`:

| Line | `terminalOs` | Runs on |
|---|---|---|
| No `creds://` reference | unset or linux | **Server**, over the exec path to the bridge's own entry (Q4's case when that entry logs in by password); the line, `command` and `commandArgs`, goes there as written, a literal typed into it included (Q10) |
| No `creds://` reference | windows | Laptop |
| Has `creds://` references | windows | **Laptop**, values in the child's environment |
| Has `creds://` references | unset or linux | **Refused**, with a sentence: the value would have to reach the server; set "Runs on" to Windows to run it on the laptop |
| A script injecting a variable, no reference | unset or linux | **Refused**, with a sentence (below) |
| A script injecting a variable | windows | Laptop, variables in the child's environment as today |

Unset means the server on a bridge door, as it does for the person's click, whether or not the line has references. Adding a reference to a line
therefore never moves it silently to another machine: it refuses until the person says so.

**The table covers Terminal and script entries alike.** A script entry gains the existing `terminalOs` "Runs on" field. On the server rows:

- The body reaches the server **over stdin**, never argv, and is not capped by the 8000-character command limit (`sshExecCommand.ts:25`). It is written to a private file in
  `~/.creds-for-devs/run/` (0700), then run by its interpreter with **stdin from `/dev/null`** and the file removed at the end. Feeding `bash -s` directly would let a script that reads stdin
  eat its own body. `sshExecRunner.ts:134` ignores stdin today; the bounded input path with end-of-file and error handling is built in E2.2 for the note (§4.3) and reused here. The interpreter is chosen for the **server**: `scriptRunAction` calls `scriptRunPlan(language, process.platform)` (`agentUseActions.ts:143`), which is the laptop's platform; a server run passes the bridge's `remoteOs`, and the server row for `python` runs `python3` (Ubuntu ships no `python`), decided in E3.1's table and tested.
- **A script that injects any variable does not run on the server**: `Object.keys(resolveScriptEnv(…).env).length > 0` (`scriptRender.ts:169`, which injects
  every enabled named variable whether or not the body mentions it, so a Python script reading `os.environ` is caught too). A variable may hold a secret and
  nothing marks which, so the refusal says so and names the two ways out: move the value to a `creds://` reference and set "Runs on" to Windows, or remove it.
  A literal secret typed into a body, or into a Terminal entry's `command` or `commandArgs`, is outside this guard, because nothing can tell it from any other string and a heuristic would promise what it cannot keep. So the limit is said where it matters: the scope pick states on every Terminal and script row that, **when run on the server**, the stored command or script text goes there as written, and that secrets belong in `creds://` references (conditional, since the revision for epoch 7: the Windows rows of the table run on the laptop and the refused rows launch nothing, so an unconditional sentence misleads on those rows) (§2, the second accepted case; §2.1 Q10, the owner's decision of 2026-11-06), a test pins that sentence, and the file holding a body lives only for the run.

A call not on a bridge door behaves exactly as today. Content trust (`isCommandTrusted`) is unchanged: the person runs the
line once by hand first. For a script in a Remote-SSH window that click confirms trust (`passScriptGates`, `commands/runCommands.ts:173`) and is then refused by the pinned
terminal (`launchScript`), so trust is recorded but the words read like a failure: they are reworded to say the agent can now run it. Running a script by a
person's click on the server is a separate todo (§8). An agent still cannot supply a command (`CommandLine.cs:129-134`). `timeoutMs` becomes sendable,
clamped by `clampExecTimeout` to 120 s. The wait ends when stdio closes (`sshExecRunner.ts:191-203`), so a script leaving a
daemon holding stdout runs to the timeout (M3).

For the laptop rows, the agent path adopts what `runWithSecrets` does for the person (`runCommands.ts:244-253`): references
resolve into the child's environment, never argv, and every resolved value joins that call's mask table. PIN and woven refusals
surface as sentences. Masking is a guard against accident only (`secretMasker.ts`); the guard against intent is that the line is
the person's, trusted, and not the agent's to change.

### 4.7 Surviving a reboot

**The intent is durable, the access is not.** Opening a bridge creates `<globalStorageUri>/bridges/<hash of account and entry>.json`, exclusively, so two windows racing get one record: `{accountId, serverEntityId, bridgeId, target}`, the
scope staying in its own record (§4.2). **The record is never rewritten:** it is created by Open and removed by Close, and those are its only changes, so a slow window has nothing to write back and cannot resurrect it. That folder is the one every window of this VS Code shares, as the announcement files already rely on (`cliEndpoint.ts`, `Endpoints.cs:55-61`). The file is written by temp-and-rename. A file rather than `globalState`, because several windows must see a Close at once.
Only *Close Remote Bridge* removes it, and that is offered in every state the record can be in, from any window. Closing or crashing a window removes nothing.

**Any window restores every saved bridge** once it is able to connect (below). Supervisors live in a window's memory, so nothing carries over from a window that ended: at activation, and again on every unlock, a window reads all records and, for each it does not already own, tries the lock and starts a new supervisor if it wins. **Activation must happen for that to run** (D13): `package.json` declares no `activationEvents`, so a restored Remote-SSH window that shows Explorer never activates this extension, and no restore or poll runs. The event is `onStartupFinished`, which activates the UI host (`extensionKind: ["ui"]`, where the records are) in every window once the editor is up. **The manifest cannot sit behind the switch** (D19): `activationEvents` is static JSON and `BRIDGE_FLOW_ENABLED` cannot gate it, and an activation is the whole of `activate()`, not the restore alone. So E2.3 builds the restore and the polls and tests them through an activation the test drives; **the manifest line lands in E4.1's flip commit**, the same commit that turns the switch on, and E2.4's switch-on VSIX adds the line at build time for M7 and never ships. The switch's test (§4.5) extends to the manifest: while the constant reads `false`, `package.json` declares no `activationEvents`. Until the flip, a restored window activates as today, when the person opens the CredsForDevs view or runs a command, and the restore runs then. **The permanent cost after the flip, stated here and in the flip's CHANGELOG entry, and told to the owner at the end of the work:** every window of every user activates this extension at startup, bridge or no bridge, which is the full `activate()`: the broker starts in the window when anything is opened to agents (`commands/agentCommands.ts:119,784-795`), the keychain and metadata toasts show (`extension.ts:151-152`), and auto-sync runs on startup where it is on. It cannot be narrowed small: VS Code activates an extension whole, `activate()` is one function at its line ratchet, and a shell that does little until a bridge record exists would be a restructuring of `extension.ts`, not a line; it is left as a stated cost, and the help names it. The restore and the polls run in the UI host of every window, local or Remote-SSH alike; nothing of this runs on the server. That
fresh attempt on unlock is also how a bridge returns when every window had been locked and nobody was trying. `VaultKeys` has `onDidLock` (`vaultKeys.ts:112`) and no unlock event, and ordinary and
recovery-code unlock are separate paths, so one `onDidUnlock` is added and both fire it.

**Exactly one window owns a bridge, by a lock the OS releases.** The owner holds a named pipe, `\\.\pipe\creds-bridge-<bridgeId>`. Measured on the owner's PC in VS Code's own Node 24: a second process
gets `EADDRINUSE` while the holder lives, and gets the pipe the moment the holder is killed. So a power-off leaves no stale claim, two windows cannot both win, and no pid is read. Linux uses an abstract socket
(`\0creds-bridge-<bridgeId>`), which the kernel also releases on death. macOS has neither, and a socket file survives a kill, so it would need probe and re-verify that must be proven: until that is tested, **a bridge on
macOS does not restore by itself**; it says so and offers Open. The durable record and the live lock are different mechanisms on purpose.

**The order is the contract.** The lock is the authority: take it, re-read the record, compare the target, re-check the account and scope, start the listener, connect, verify, and only then publish the note. Nothing is published
or swept without the lock held, and a previous owner's late verify, publish or cleanup cannot touch the new owner's note or socket because the handover itself rules it out: the old owner is dead, or it closed and cancelled before it released (§4.3, generations).

- **Claim only when able to connect**, a predicate with five clauses, tested as one function with the clock, the uptime and the hold injected: (1) the window's vault is not locked (`LockState.isLocked()`); (2) the entry's credential opens with no gesture (`resolveSshCredential` answers `storedKey`, `keyPath` or `password`, not `stopped`: a PIN-sealed or woven credential needs the person, and the row says so); (3) the record's `target` equals the entry's current user, host and port; (4) the account is still present; (5) **the bridge is not held**, below. A locked window does not claim.
- **The hold** (Q9, D17). A window that locks, by any road into `VaultKeys.lock()` (the idle timer and *Lock Vaults* through `lockNow.ts`, a corporate eviction through `evictAndLock`, `corpBindingWiring.ts:151-159`; `lock()` gains a cause, `idle | person | corporate`, and for `corporate` the account, carried on `onDidLock`), writes `bridges/<hash>.hold`: `{bridgeId, cause, accountId?, lockedAt, uptimeAtLock}`, temp-and-rename, where `uptimeAtLock` is `os.uptime()` in seconds, **as the first step of the close, before anything is closed and before the pipe is released**: a crash mid-close then leaves a hold, which fails toward held. **Which records get a hold is the cause's**, because `LockState` is per window (`vaultKeys.ts:116`) and a lock in one window reaches a bridge another window owns only through the file (the owner's "holds across windows"): an `idle` lock writes one for each bridge that window owns; a `person` lock (*Lock Vaults*) writes one for **every** record, owned or not, because the click is the person's word for the whole machine; a `corporate` lock writes one for every record of **that account** and upgrades an `idle` or `person` hold standing on them. The owner's 5 s re-read of its record (below) reads the hold too, and a hold the owner did not write runs the five-step close in the owner; so *Lock Vaults* in the front window closes a bridge a background window owns within 5 s, and after a restore, when any window may be the owner, the same holds. Clause 5 reads the hold fresh on every evaluation: a held bridge is claimed only when the hold is cleared, which happens in exactly three ways for `idle` and `person`, and in neither of the first two for `corporate`. **A person's act in this window later than the hold:** an unlock (`noteUnlocked`) or a touch of the vault (`noteUserActivity`), or the *Reopen* button on the bridge's row, which is a touch (in a window whose vault is locked, *Reopen* runs the unlock first: a touch leaves clause 1 false); later is compared on uptime within one boot, never on the wall clock; `LockState` records the last person's act separately from the idle clock's base, because the arm below must not count as one. **An agent's call never counts as a person's act:** `brokerConsent.ts:137` counts only an Allow or Deny click, but `runVpn` calls `noteUserActivity()` unconditionally (`vpnRun.ts:75`) and an agent's `up` or `down` reaches it through `agentVpnOpener` (`:40`), so under `quiet` with `never` a local agent's `up` would lift the hold in its window, and today, on `main`, it postpones the idle lock for the local doors. The call is guarded on `startGate === undefined` (a person's act is never recorded from an agent path), with a test, in the partial-E1 closing commit, since it is one line that corrects a shipped local behaviour; E2.3's lock tests assert it. **A reboot**, for a hold whose cause is `idle` or `person`: recognised when `os.uptime() < uptimeAtLock`; the hold file is removed when the pipe is acquired on that reading, so a connect that then fails cannot re-hold the bridge once uptime passes `uptimeAtLock`. Uptime is the kernel's tick count (`/proc/uptime` on Linux, `GetTickCount64` on Windows), monotonic within one boot and reset by a boot, so a wall-clock step, forwards or backwards, cannot make a reload look like a reboot or a reboot look like a reload; the wall clock is not consulted for this. It misses a reboot when the machine has already been up longer than it had been at the lock before a window evaluates; then the bridge stays held and the row offers *Reopen*: the miss fails toward held, and it is a test (§7). For an idle lock the miss needs the machine to have been up, before the first window opens, longer than it had been when the lock landed (at least `autoLockMinutes` after the previous boot): a window opened sooner than that reads the reboot, one opened later stays held. **A Windows shutdown under Fast Startup** (`HiberbootEnabled=1`, the default where hibernation is on; the owner's own PC has it) keeps the tick count, because the kernel session hibernates: *Shut down* then power-on reads as no reboot and the hold stays, while *Restart* resets the count and clears it. It fails closed, and it narrows the owner's "a reboot clears it" to *Restart* on such a machine (Q9 and the help say so; M7 measures both). Under WSL, in a container and on macOS the reboot reading is refused and reads as held (E2.3): `wsl --shutdown` resets a WSL kernel's uptime with no reboot, so a VS Code build that itself runs in WSL would read one; a container's uptime is its host's or its own by runtime; macOS derives uptime from the wall clock and is outside this path already (it does not restore by itself). `extensionKind: ["ui"]` keeps a Remote window's host on the laptop, so a Remote-SSH window reads Windows there. A malformed hold or a failed uptime read means held; a hold that cannot be written keeps the pipe. **Close** removes the hold with the record. **A `corporate` hold is cleared by no local act, not by *Reopen* and not by a reboot:** an eviction is the server's word that the account is deactivated. It ends in two ways only: the standing gate reads the account active again (clause 4 reads `lockedReason` for the record's account, `corpLease.ts:75`, and claims only on `''`, so a deactivated or lease-expired account never claims, hold or no hold; when it answers `''` again the hold is removed at the next evaluation), or *Close*. A window that crashes or is closed outside a lock writes no hold, so that takeover stays automatic, and a hold whose record is gone is swept. The hold is read, never trusted further than clause 5: it says who may claim, and the lock in the window stays the authority on what the vault does.
- **The order of a lock's close** (D20), tested with a spawner stub and an in-flight call: (1) the bridge's door stops admitting: every new call answers `vault_locked` (409, added to `contract/broker-v1.json` in E2.1, `errors` and `exitCodes`), *The vault is locked on the laptop. Unlock it there; nothing ran.*; (2) every admitted call not yet launched (waiting in a dialog, in the gate, before its spawn) is answered `vault_locked` with the same sentence, its dialog defused as §4.10 defuses a left dialog; (3) every running child is killed, explicitly, and its caller answered **nothing** on purpose: the client sees EOF and reads it as *may or may not have run* (`Program.cs:235`), which is the truth for a spawned exec, where *nothing ran* would be false and would invite a second run; (4) the listener's responses are flushed within a bound (2 s), then `server.close()` and `closeAllConnections()` (`brokerBridgeListeners.ts:74-80`), the tunnel killed, its waits cancelled, the note left for the next connection or the sweep; (5) the pipe released. The hold is written before step 1 (above), so a crash anywhere in the five steps leaves the hold and never an unheld pipe. **For the spec, traced:** a closing listener kills a running child only indirectly, through the request's abort: `closeAllConnections()` destroys the response, `abandonedWhenClosed` (`requestLife.ts:22-34`) aborts the request's signal, and `runBounded` kills on it (`sshExecRunner.ts:146-163`, SIGTERM then SIGKILL after `KILL_GRACE_MS`); the window's own signal fires only on `dispose`. Step 3 is therefore explicit in the lock path, not left to the close, so the order is knowable and the test can hold end to end. A client that finds every note's socket dead says *The bridge's laptop window is locked, closed or reconnecting. Unlock the vault or open a window on the laptop; nothing ran.*, once, with no retry loop (E2.1); it fires on a network drop too, where "reconnecting" is the true word (§7 *Reconnect* expects "down" and reads this sentence); neither is `busy`, which means a dialog stands.
- **A claim arms the idle clock without touching the lock** (Q9, D18): `LockState` starts unlocked with no `lastActivity`, so an untouched window never locks (`lockState.ts:14,102`). `noteUnlocked` is the wrong method: it clears `locked` (`lockState.ts:68-71`), so a lock landing between the predicate and the arm, during a connect of several seconds, would be undone with no gesture, and it overwrites a real person's clock. So `LockState` gains `armIdleClock(now)`, which does `lastActivity ??= now` and nothing else, exposed through `VaultKeys`, and every claim calls it, a restore or a takeover alike: the vault locks `autoLockMinutes` after boot unless a person touches it, a lock during the connect stays a lock, and a clock a person set does not move. *Open Remote Bridge* and turning `quiet` on warn when auto-lock is on, naming `credSshManager.autoLockMinutes`, its value, and the hour the bridge would close, with one button that opens the setting (E2.2, with a test on the sentence).
- **Windows not owning a bridge** try the pipe every 30 s, so a surviving window takes over when the owner closes.
- **Close** removes the record, the hold and the scope record; the owner re-reads its record every 5 s and shuts down, so revocation from another window takes at most 5 s, and from the owner's own window it is immediate. A retry never brings it back.

**A restored bridge restores only what was opened.** The record's `target` is compared with the entry's current user, host and port. If the entry now points elsewhere, the bridge does not come back, and its row says why and offers Open:
otherwise a scope would silently follow an edited entry to another machine. A PIN-protected or woven credential cannot open unattended, so that row says "needs you" and does not loop.

**A Close from a window that does not own the bridge removes the record; the owner then removes the note.** After a power-off there is no owner, so the note stays until a sweep on that server finds its socket dead, which is harmless by §4.3's argument.

**What a person sees:** after a reboot the row reads *restoring* (the vault starts unlocked, D13, so *waiting for unlock* is shown only when a window has locked since), then *needs you* for a PIN-sealed or woven credential, else connecting, then up. A held bridge reads *locked in a window at <time>; unlock or touch the vault here, or Reopen*, with the *Reopen* button; a `corporate` hold reads *the account is blocked*, with no button. The agent door row (`agentDoors.ts:96`) says the bridge reopens by itself until closed. On the server nothing needs doing: the stable `bridgeId`
lets the new connection unlink its own old sockets, the note is rewritten with the new port and key, and clients read notes per call.

## 6. Growth surfaces

| Surface | Size | Retired by | If interrupted |
|---|---|---|---|
| Bridge listeners | One per open bridge; single digits | Close and `dispose` | Dies with the extension host |
| Scope records in the shared storage folder | Under 1 KB per server; at most one per entry a person bridged | *Close Remote Bridge* removes it together with the bridge's record | Temp-and-rename, so an interrupted write leaves the old file; a leftover temp file is removed at the next write |
| Notes on the server | One per live bridge; single digits | Overwritten per connection; removed on Close and by the sweep when the socket is gone | A stale note is harmless (§4.3) |
| Sockets on the server | One per connection, sshd leaves them behind (`sshBridge.ts:339-357`) | A bridge unlinks its own earlier ones at each connect, listening or not, so a flapping link holds at most one; others swept when `ss` exists | Without `ss`, at most one dead file per bridge ever opened, each under 100 bytes of directory entry; said once to the person |
| Per-bridge prompt windows | One small list of timestamps per open bridge | Gone with the listener | In memory only |
| Reconnect loop | One timer per bridge | Close or window end | Dies with the extension host |
| Bridge records in the extension's storage | Under 1 KB per bridge; one per bridge a person opened | Removed by Close alone (§4.7: created by Open, removed by Close, never rewritten); a record whose entry no longer exists is not restored, and its row says so and offers Close | Kept deliberately: that is the feature |
| Hold files in the extension's storage (§4.7) | Under 200 bytes; at most one per bridge record | Removed by Close with the record; an `idle` or `person` hold cleared by a person's act or a reboot (then removed at the pipe's acquire); a `corporate` hold removed when the standing gate reads the account active again; a hold whose record is gone is swept at the next evaluation | The hold is written before the close begins, so a crash mid-close leaves a hold and the bridge waits for a person's act or a reboot: the side the design accepts (it fails toward held). A crash outside a lock writes none, and that takeover is automatic |
| Polls for §4.7 | One timer per record per window: non-owners try the lock every 30 s, the owner re-reads its record every 5 s | Close or window end | Dies with the extension host |
| Ownership pipes | One per owned bridge | Released by the OS on process death | Nothing is left after a power-off |
| Script files on the server, `~/.creds-for-devs/run/` | One per running script, at most the exec-slot cap (8), each the size of its body | Removed when the run ends; leftovers swept at the next connect | A killed run leaves one file until then; it holds no variable, because a script with variables does not reach the server |
| Per-call `ssh_config` files in the keys folder (§4.9) | One per running bridged call, at most the exec-slot cap (8), under 2 KB; no value in it | Removed in the call's `finally` with its key files; the purge of the keys folder on activate and deactivate covers a killed window | At most 8 left until the next activate |
| Hop key files in the keys folder | One per hop per running call, at most 4 × 8, 0600 | The same | The same; a leftover is the person's own key in a folder only they can read, as the materialised destination key is today (Amendment 3, C.6) |
| `<globalStorageUri>/bridges/known_hosts` (§4.9; not in the keys folder, whose purge would erase it at every activate) | One file, one line per host a bridged call first met unpinned | Kept: it is the record of first contacts; the person may delete it; a pinned entry never reads it | Written by `ssh` itself |
| Journal lines from a handler that throws (`unanswered`, §4.1; D21) | One line per throw until E2.2b; then at most one per door per minute, the next line carrying the count of what it stands for | The limiter of §4.1 (E2.2b, before R1 goes); the journal file's own retention is not changed by this plan | At partial E1 the path is reached only by a handler no caller has been shown to make throw; on a bridge door the key-holder's rate is bounded by nothing else, so the limiter precedes R1's removal |

## 9. Definition of Done

- [ ] On the owner's server, in tmux, Claude lists and uses through `creds-mcp` exactly the entries scoped to that server, and an entry
      outside the scope is indistinguishable from one that does not exist; **a listed row carries only §4.2's named fields**, so no connection string and no command text crosses.
- [ ] A script entry the agent runs, `vpn-up` as the agent's login among them, runs on the server, after a consent on the laptop, and returns its exit code and output. The bridge's entry for that login is one of the owner's imported `Host` blocks (§2.2), checked in M8 (6) before E1.6 is specified.
- [ ] A command using a password runs on the laptop; the agent sees only masked output.
- [ ] A database query runs from the laptop, and its password never reaches the server.
- [ ] Closing the window ends all access, with a clear message; reopening restores it, with no action on the server.
- [ ] **After a reboot of the PC, the bridge returns by itself once a window is open and the vault unlocked**, and only *Close Remote Bridge* ends it; a PIN-sealed or woven credential reads *needs you* and does not loop, and a `corporate` hold stays, as §4.7 already says.
- [ ] A dropped network recovers by itself; nothing is replayed; a running `creds-mcp` needs no restart.
- [ ] **No secret value persists on the server and none is served to it:** a file listing of the server before and after a run of every action shows no persisted secret value, and no body a served route returns to the bridge carries a secret value (§4.2's read shape; the `exec` and `query` outputs are what the agent asked for, masked by the call's mask table). **Carved out, in these words:** the password of a password entry whose destination is that server itself, sent to that server's `sshd` on every connection (Q4, the owner's exception), and any stored line that runs on the server under decision 6 with whatever the person typed into it, a script entry's body and a Terminal entry's `command` with its `commandArgs` alike, while a value by `creds://` reference never crosses (Q10, the owner's second exception). **The check is two checks, stated apart.** *During execution*, the values present on the server are exactly the two carve-outs: Q4's password in `sshd`'s hands, and a stored line's text with whatever literal it holds, in the private file under `~/.creds-for-devs/run/` and in the interpreter's argv or memory for the length of the run, **intentionally observable by the agent on that server**, since the agent is what runs it. *After execution*, nothing persists: the temporary script file is removed, and a file listing before and after shows no value of either carve-out, and no referenced value at any time. The matching tests (§7 *Secrets*, *Read shape*, *Scripts on the server*, *Run site*) assert both halves and nothing wider: a literal in a body or a `commandArgs` value is in the server's file listing during the run and gone after it; a referenced value never appears in any listing, argv or served body, during or after.
- [ ] **Every `ssh` a bridge spawns keeps §4.9:** no bridged call reads `~/.ssh/config` or the system file, consults an agent or a default identity, hands the destination's password to a hop, or carries the extension host's environment; the SSH-contract tests of §7 are green in CI and M8 and M9 are recorded.
