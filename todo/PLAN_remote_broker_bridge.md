> named pipe рядом с loopback-TCP), мост в WSL, мост в Remote-SSH, и — отдельной фазой, зависящей от

## 1. Симптом

Разработчик работает в **WSL** (основной сценарий) и, реже, через **Remote-SSH**. Код, терминал,
`git`, скрипты исполняются там. Хранилище — на Windows-стороне. Сегодня это значит: либо копировать
секреты внутрь (ровно то, чего инструмент существует не делать), либо не пользоваться инструментом в
основном рабочем окружении.

**Цель:** скрипт/`git`/CLI внутри WSL или на удалённом хосте просит секрет; модал подтверждения
выходит на **локальной Windows-машине**; на той стороне секрет не появляется никогда.

## 2. Что уже есть

**Важнее, чем кажется:** `package.json:47-49` объявляет `"extensionKind": ["ui"]`. Расширение
**всегда** работает на локальной машине, даже когда рабочая область — WSL или удалённый хост. Значит
криптография и секреты остаются локально **по построению**, модал по определению выходит там, где
сидит человек, и не нужно решать, какая половина расширения где живёт. Предпосылка выполнена.

Дальше:

| Что | Где | Годность |
|---|---|---|
| Дисциплина «секрет только в env порождённого нами процесса или как capability-токен» | вся кодовая база; ключи — только `keys/<pid>/` 0600, вычищаются | политическая половина фичи уже соблюдена |
| `(kind, action)` реестр | `useActions.ts` | вызывающий с той стороны получает те же возможности без правок HTTP-слоя |
| Контракт провода | `brokerProtocol.ts` | транспорт-агностичен по содержанию |
| Запуск `ssh` с учёткой из хранилища | `sshExecCommand.ts`, `sshCredential.ts`, `sshAskpass.ts`, `runBounded` | **мост для Remote-SSH строится из этого же** — см. §5 |
| CLI на обеих сторонах | [PLAN_headless_cli.md](PLAN_headless_cli.md): win-x64/arm64 **и** linux-x64/arm64 | меняет всё в WSL-пути — см. §4 |

## 3. Что мешает

**Г-1. Брокер слушает только loopback-TCP.** `startLoopbackServer` (`loopbackServer.ts:13-22`):
`listen(0, '127.0.0.1')`, и в файле стоит комментарий, что это **сознательно**. Из WSL2
`127.0.0.1` — это loopback **виртуальной машины**, где не слушает никто. Unix-сокета в кодовой базе
нет вообще.

**Г-2. Логики проброса нет.** Ни `asExternalUri`, ни devcontainer/WSL-осведомлённости — ноль
вхождений по репозиторию.

**Г-3. Направление обратное тому, что даёт VS Code.** Встроенный port-forwarding показывает
**локальному** клиенту сервис, работающий **на удалённой** стороне. Нам нужно наоборот. Это
семантика `ssh -R`, а не то, что VS Code делает сам.

**Г-4. Поверхности ssh-агента нет** (для фазы 4): ничто не реализует протокол `ssh-agent`,
`SSH_AUTH_SOCK` не упоминается. Расширение умеет «сам запускаю `ssh`», а не «подписываю по запросу
чужого `ssh`».

## 4. Фаза 2 — WSL (основной сценарий)

Решение владельца делать CLI на .NET AOT **для Windows и для Linux сразу** даёт здесь путь чище,
чем принятый в экосистеме `npiperelay.exe` + `socat`: **обе половины моста наши**.

### Путь A — interop-exec (по умолчанию, без настройки)

WSL по умолчанию умеет запускать Windows-бинари (interop включён; `/proc/sys/fs/binfmt_misc/WSLInterop`).
Значит Linux-`creds` внутри WSL, обнаружив WSL (`WSL_DISTRO_NAME`, `/proc/version` c `microsoft`),
**перезапускает Windows-бинарь** `creds.exe` с теми же аргументами и пробрасывает stdin/stdout/stderr
и код выхода. Windows-половина говорит с брокером по своей петле.

Почему это правильный основной путь:

- **ноль настройки** — не нужен ни mirrored networking, ни правило файрвола, ни сторонние утилиты;
- **ничего не слушает наружу** — брокер как был loopback-only, так и остался;
- аргументы CLI — псевдонимы и команды, **не пути**, поэтому трансляция путей WSL↔Windows не нужна;
- работает на WSL1 и WSL2 одинаково.

Цена: одна лишняя раскрутка процесса на вызов (для AOT-бинаря это единицы миллисекунд) и требование,
чтобы `creds.exe` был на Windows-стороне — что и так следствие плана CLI.

### Путь B — собственный relay (нужен для сокета: git, ssh, фаза 4)

Когда нужен **настоящий unix-сокет** внутри WSL (например `SSH_AUTH_SOCK` или что-то, что умеет
только сокет, а не exec):

```
creds relay --socket /run/user/<uid>/creds.sock
```

слушает unix-сокет внутри WSL и на каждое соединение поднимает через interop
`creds.exe --stdio-bridge`, перекладывая байты в обе стороны. Это замена связки
`npiperelay + socat` **одним бинарём, обе половины которого наши** — не требует от пользователя
ставить сторонние утилиты и не зависит от их совместимости.

### Путь C — mirrored networking (оппортунистически)

Если у пользователя Windows 11 с `networkingMode=mirrored` в `.wslconfig`, `127.0.0.1` из WSL
попадает на Windows-петлю, и TCP работает напрямую. `creds doctor` это обнаруживает и сообщает как
быстрый путь. **Не требовать** — только использовать, если уже есть.

## 5. Фаза 3 — Remote-SSH

Здесь красивое переиспользование: **мост поднимается тем же `ssh`, которым расширение и так умеет
ходить, с той же учёткой из хранилища.**

- `ssh -R /remote/path/creds.sock:<локальный сокет или pipe-прокси>` — RemoteForward с unix-сокетами
  (OpenSSH ≥ 6.7 с обеих сторон). Аргументы строит `buildSshExecArgv` (`sshExecCommand.ts`), учётку
  даёт `resolveSshCredential`, пароль — через уже существующий askpass. Соединение живёт как
  фоновый `runBounded`-процесс с `AbortSignal`, привязанным к окну.
- На удалённой стороне нужен `creds` (linux-x64/arm64 — их же собирает план CLI). Первый запуск может
  предложить **скопировать бинарь** по тому же ssh (`scp`), либо человек ставит сам. Решение —
  §8.2.
- Переиспользовать соединение, которое держит VS Code, из расширения нельзя — оно не выставлено в
  API. Поэтому своё, при желании с `ControlMaster`/`ControlPath`, чтобы не плодить сессии.
- Модал согласия — на Windows, автоматически: брокер локальный.

## 6. Фаза 1 — предпосылка обеих (делается первой)

`startLoopbackServer` дополняется вторым слушателем на том же `handle`:

- **Windows:** named pipe `\\.\pipe\creds-<pid>` (это то, к чему мостится путь B из §4).
- **POSIX:** unix-сокет `<globalStorage>/broker-<pid>.sock`, 0600 через существующий `lockToOwner`.

Это же немедленно улучшает локальный CLI-путь: права файловой системы вместо «любой локальный
процесс может постучаться на порт».

## 7. Порядок сборки

1. **Фаза 1**: `brokerListeners.ts` (TCP + pipe/сокет), права, уборка при `dispose`, тесты. Ничего
   внешнего не меняется.
2. **Фаза 2 (WSL)**: определение WSL в CLI, путь A (interop-exec), `creds doctor` показывает, каким
   путём пойдёт; e2e внутри WSL. **Это основной сценарий владельца — он должен работать первым.**
3. Путь B (`creds relay`) — когда понадобится сокет (git/ssh внутри WSL), не раньше.
4. **Фаза 3 (Remote-SSH)**: `ssh -R` поверх существующего построителя argv, доставка бинаря на
   удалённую сторону, e2e на живом хосте.
5. **Фаза 4 (ssh-агент)** — отдельным планом, только после разморозки D1.
6. Dev Container — **последним или никогда**; если понадобится: bind-mount сокета плюс строка в
   `devcontainer.json` пользователя.

## 8. План тестирования

- Фаза 1: оба слушателя отвечают одинаково (табличный тест); права 0600 / ACL на Windows; сокет и
  pipe исчезают при `dispose`; чужой пользователь не открывает сокет (проверяется в Linux-CI).
- **WSL, e2e на живой системе** (автоматизировать нельзя целиком — GitHub Actions не даёт WSL с
  интеропом в нужной форме, значит это ручной чек-лист в DoD): внутри дистрибутива
  `creds ssh <alias> -- echo hi` → модал на Windows → вывод в WSL-терминале → **`find` по файловой
  системе WSL до и после показывает, что ни одного файла с секретом не появилось**.
- WSL: путь A выбирается по умолчанию; путь C — только если mirrored уже настроен; `doctor`
  правильно называет выбранный путь.
- Отрицательный тест: WSL **без** interop (отключён в `wsl.conf`) — внятная ошибка с указанием
  причины, а не «connection refused».
- Remote-SSH: e2e на живом хосте, тот же `find`-чек; обрыв соединения → CLI сообщает, а не висит;
  закрытие окна убивает `ssh -R` (проверка `AbortSignal`).
- Код выхода удалённой команды проходит через оба моста без изменений.

## 9. Definition of Done

- [ ] Брокер слушает pipe/сокет наравне с loopback-TCP, с правами только для владельца.
- [ ] **WSL работает** end-to-end и проверен руками; путь по умолчанию не требует никакой настройки
      от пользователя.
- [ ] **Remote-SSH работает** end-to-end и проверен руками на живом хосте.
- [ ] Для обоих доказано перечислением файлов до/после, что на той стороне не появляется секретов.
- [ ] Модал согласия всегда на локальной машине; удалённая сторона не может его подавить.
- [ ] Документация говорит, какие контексты поддержаны (WSL, Remote-SSH), какой не поддержан
      (Dev Container) и почему — без «в целом работает».
- [ ] Фаза 4 не начата без разморозки D1.

## 10. Открытые вопросы

1. Путь B (`creds relay`) — делать сразу вместе с WSL-фазой, или дождаться первого реального случая,
   когда нужен именно сокет (git внутри WSL)? *Предложение: дождаться; путь A закрывает CLI-сценарий
   целиком.*
2. Remote-SSH: предлагать ли автоматическую доставку `creds` на удалённый хост по `scp`, или только
   печатать команду установки? *Предложение: печатать команду; автокопирование бинаря на чужой хост
   — это то, что пользователь должен решать сам.*
3. Нужна ли поддержка нескольких одновременных контекстов (WSL + два удалённых хоста) в первой
   версии, или один за раз достаточно?
