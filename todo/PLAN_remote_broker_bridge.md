# PLAN — Мост брокера в Remote-SSH / Dev Container / WSL

> Status: **plan only, nothing implemented yet.** Scope: новый транспортный слой брокера (unix-сокет
> рядом с loopback-TCP), проброс в удалённый контекст, и — отдельной фазой — поверхность
> ssh-агента. Самая крупная из пяти фич: **готового кода почти нет** (~10–15 %).
>
> Related docs: [module_extension.md](../research/module_extension.md#the-agent-broker--using-a-credential-without-handing-it-over),
> [architecture.md](../research/architecture.md), [PLAN_headless_cli.md](PLAN_headless_cli.md)
> (общий контракт и клиент), [PLAN_audit_roadmap_2026_08_25.md](PLAN_audit_roadmap_2026_08_25.md).
> Пункт D1 дорожной карты (локальный ssh-agent) владельцем **отложен**; фаза 3 этого плана — его
> удалённый родственник и без D1 не имеет смысла, поэтому она здесь помечена как зависимая.

---

## 1. Симптом

Senior-разработчик работает через **Remote-SSH**, в **Dev Container** или в **WSL**. Код, терминал,
`git`, скрипты — всё исполняется в удалённом контексте. Хранилище — на локальной машине. Сегодня это
означает: либо копировать секреты на удалённый хост (ровно то, чего инструмент существует не делать),
либо не пользоваться инструментом в основном рабочем сценарии.

**Цель:** скрипт/`git`/CLI внутри удалённого контекста просит секрет, модал подтверждения выходит на
**локальном** ПК, на удалённом диске секрет не появляется никогда.

## 2. Что уже есть — и что из этого важно

**Хорошая новость, важнее, чем кажется:** `package.json:47-49` объявляет
`"extensionKind": ["ui"]`. Расширение **всегда** работает на локальной машине, даже когда рабочая
область — удалённый хост, контейнер или WSL. Значит:

- вся криптография и все секреты остаются локально **по построению**, без единой правки;
- нет «раздвоения» — не нужно решать, какая половина расширения где живёт;
- модал согласия по определению выходит там, где сидит человек.

Это ровно та предпосылка, которая для этой фичи нужна, и она уже выполнена.

Дальше — то, на что опереться:

| Что | Где | Годность |
|---|---|---|
| Дисциплина «секрет только в env порождённого нами процесса или как capability-токен» | вся кодовая база; ключи материализуются лишь в `keys/<pid>/` 0600 и вычищаются | политическая половина фичи уже соблюдена |
| `(kind, action)` реестр | `useActions.ts` | удалённый вызывающий получает те же возможности без правок HTTP-слоя |
| Контракт провода | `brokerProtocol.ts` | транспорт-агностичен по содержанию |
| Клиент | `agentCli.ts` (и будущий Rust-бинарь) | тот же клиент годится внутри контейнера |

## 3. Что мешает — и это настоящий greenfield

**Г-1. Брокер слушает только loopback-TCP.** `startLoopbackServer` (`loopbackServer.ts:13-22`):
`server.listen(0, '127.0.0.1')`, и в файле стоит комментарий, что это **сознательно** — «ничто,
поданное так, не достижимо с другой машины». Из контейнера `127.0.0.1:<порт>` — это loopback
**контейнера**, где не слушает никто. Unix-сокета в кодовой базе нет вообще (проверено по
`AF_UNIX`/`.sock`).

**Г-2. Нет никакой логики проброса.** Ни `asExternalUri`, ни `registerRemoteAuthorityResolver`,
ни знания про devcontainer/WSL — ноль вхождений по всему репозиторию.

**Г-3. Направление проброса — обратное тому, что даёт VS Code из коробки.** Встроенный
port-forwarding Remote-SSH предназначен показать **локальному** клиенту сервис, который работает
**на удалённом** хосте. Нам нужно наоборот: локальный сервис, достижимый **изнутри** удалённого
контекста. Это семантика `ssh -R`, а не то, что VS Code делает по умолчанию.

**Г-4. Поверхности ssh-агента нет.** Ничто не реализует протокол `ssh-agent`; `SSH_AUTH_SOCK` в
репозитории не упоминается. Расширение умеет «сам запускаю `ssh`», а не «подписываю по запросу
чужого `ssh`». Это **другая по форме возможность**, чем всё, что есть в `sshCredential.ts` /
`sshExecCommand.ts` / `sshAskpass.ts`.

## 4. Три фазы, каждая полезна сама по себе

### Фаза 1 — unix-сокет как второй транспорт брокера (локально)

Цель: развязать «что слушает» и «что делает». `startLoopbackServer` дополняется вторым слушателем:
`http.createServer` на **unix-domain socket** (`<globalStorage>/broker-<pid>.sock`, 0600 через
`lockToOwner`; на Windows — named pipe `\\.\pipe\creds-<pid>`). Обработчик — тот же `handle`.

Почему это первая фаза, а не деталь: сокет-файл — это **то, что можно пробросить**, а TCP-порт —
нет. И это же немедленно улучшает историю CLI-пути из [PLAN_headless_cli.md](PLAN_headless_cli.md)
(права файловой системы вместо «любой локальный процесс может стучаться на порт»).

Тесты: оба транспорта отвечают одинаково; права сокета; удаление при `dispose`; на Windows — pipe.

### Фаза 2 — проброс сокета в удалённый контекст

Три контекста, три механизма — и каждый нужно проверять на живой системе, а не по документации:

| Контекст | Механизм | Что проверить |
|---|---|---|
| **WSL** | сокет виден через `/mnt/c/...`? **Нет** — unix-сокеты не работают через drvfs. Значит: TCP на адрес хоста WSL2 + токен, либо `socat`-мост. | что именно достижимо из дистрибутива без прав администратора |
| **Dev Container** | bind-mount каталога с сокетом внутрь контейнера (как это делает 1Password/gpg-agent) + `--mount type=bind`. Требует, чтобы контейнер поднимался с этим монтированием → правка `devcontainer.json` пользователя. | можем ли мы попросить пользователя добавить одну строку, или обязаны сгенерировать её сами |
| **Remote-SSH** | `ssh -R /remote/path.sock:/local/path.sock` (RemoteForward с unix-сокетами, OpenSSH ≥ 6.7). Управляет туннелем **VS Code**, а не мы → скорее всего нужен собственный `ssh -R`-канал рядом. | есть ли способ переиспользовать уже открытое соединение VS Code; если нет — цена второго соединения |

**Ключевое проектное решение фазы 2:** внутри удалённого контекста должен оказаться **только клиент
и путь к сокету** — ни ключа, ни `.enc`, ни токена долгоживущего. Токен, если он вообще нужен,
выдаётся на одну сессию и умирает с ней (механика уже есть — `grantRegistry` с idle-TTL из 0.57.0).

**Что здесь придётся признать честно:** каждый из трёх контекстов — это отдельная, реально
проверяемая на железе задача, и ни один нельзя закрыть «в общем виде». План должен разрешать
доставить их по одному: сначала тот, которым пользуется владелец (**вопрос §8.1**).

### Фаза 3 — поверхность ssh-агента (зависит от отложенного D1)

Только после фазы 2 и только если D1 (локальный ssh-агент) разморожен: реализовать подмножество
протокола `ssh-agent` (`SSH2_AGENTC_REQUEST_IDENTITIES`, `SSH2_AGENTC_SIGN_REQUEST`) на том же
сокете и пробросить его как `SSH_AUTH_SOCK`. Тогда `git push` внутри контейнера подписывается
локальным ключом, который контейнер никогда не видел.

Это самая ценная часть для «git внутри dev-контейнера», и самая дорогая: свой протокольный парсер,
подпись без выдачи ключа, подтверждение на использование. Отдельным планом, когда фаза 2 живёт.

## 5. Порядок сборки

1. Фаза 1: `brokerListeners.ts` (TCP + unix/pipe), права, уборка, тесты. Ничего внешнего не меняется.
2. Клиент (node и Rust) учится говорить через сокет/pipe; `creds doctor` показывает оба транспорта.
3. Фаза 2, **один контекст** — по выбору владельца (§8.1): обнаружение (`vscode.env.remoteName`),
   инструкция или автоматика, e2e-проверка на живой системе, документация с ограничениями.
4. Остальные два контекста — по одному, каждый со своей проверкой.
5. Фаза 3 — отдельный план, после разморозки D1.

## 6. План тестирования

- Фаза 1: юнит-тесты на оба слушателя; права 0600 (и ACL на Windows); сокет удаляется при dispose;
  чужой пользователь не может открыть сокет (проверяется на CI под Linux).
- Клиент: одинаковое поведение через TCP и через сокет (табличный тест).
- Фаза 2 (для выбранного контекста): **e2e на живой системе** — внутри контекста запустить
  `creds ssh <alias> -- echo hi`, увидеть модал на локальной машине, получить вывод, и **проверить,
  что на удалённом диске не появилось ни одного файла с секретом** (это отдельная проверка, а не
  вывод из общих соображений: `find` по контейнеру до/после).
- Отрицательный тест: удалённый контекст **без** проброса не должен получать доступ вообще (не
  «случайно работает через TCP»).

## 7. Definition of Done

- [ ] Брокер слушает сокет/pipe наравне с loopback-TCP, с правами только для владельца.
- [ ] Для **как минимум одного** удалённого контекста путь работает end-to-end, и это проверено
      руками на живой системе, а не только тестом.
- [ ] Доказано (перечислением файлов до/после), что на удалённой стороне не появляется секретов.
- [ ] Документация говорит, какие контексты поддержаны, а какие нет — без «в целом работает».
- [ ] Модал согласия всегда на локальной машине; удалённая сторона не может его подавить.
- [ ] Фаза 3 не начата без разморозки D1.

## 8. Вопросы, без которых фазу 2 начинать нельзя

1. **Какой контекст первый?** Remote-SSH, Dev Container или WSL — которым пользуется владелец
   каждый день? Это определяет и механизм, и то, что вообще можно проверить.
2. Допустимо ли просить пользователя добавить строку в `devcontainer.json` (mount сокета), или
   расширение должно уметь это само?
3. Для Remote-SSH: приемлемо ли открывать **второе** ssh-соединение (`ssh -R`) рядом с тем, что
   держит VS Code, или обязательно переиспользовать существующее?
4. Нужна ли поддержка **нескольких** одновременных удалённых контекстов (два контейнера + WSL) в
   первой версии, или один за раз достаточно?
