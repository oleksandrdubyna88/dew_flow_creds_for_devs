## 0. Что закрыто живым хостом (2026-08-26)

Владелец дал доступ к настоящей машине (Ubuntu, OpenSSH 9.6p1). Проверки шли через изолированный
sshd на loopback со своими ключами в `/tmp`; настоящий sshd, его конфиг и `authorized_keys` не
трогались.

| проверено | результат |
|---|---|
| `ssh -R` поднимает сокет с тем argv, что строит расширение | да |
| **реальные права сокета** | `srw-------`, режим **600** |
| **чужой пользователь** (`nobody`, каталог 755, то есть проверялся режим самого сокета) | `curl: (7) Failed to connect` — граница держит |
| HTTP реально течёт через проброшенный сокет | да: `{"ok":true,"service":"creds-for-devs-agent"}` |
| `ExitOnForwardFailure` делает неудачу громкой | да: `Error: remote port forwarding failed for listen path …` |
| сокет остаётся после конца сессии | **да** — отсюда уборка |
| команда уборки (та самая, что шлёт расширение) | труп снесён, живой сокет сохранён и продолжил отвечать |

**Что это опровергло:** два флага в argv (`StreamLocalBindMask`, `StreamLocalBindUnlink`) были
**инертны** — при `-R` сокет создаёт sshd, значит решают серверные копии. Клиент просил маску
`0000`, сокет всё равно вышел 600. Оба удалены; режим теперь наблюдается и о широком
предупреждается, а мусор убирается (`sweepCommand`).

## 1. Осталось: живой клик по *Open Remote Bridge*

Транспорт под командой проверен целиком. Не проверено одно — что **сама команда расширения**
собирает argv, запускает `ssh`, показывает инструкции и снимает мост при закрытии окна. Вызвать
команду VS Code со стороны агента нельзя, поэтому это остаётся кликом человека.

Что наблюдать при клике:

- мост поднялся, инструкция скопировалась, в ней путь сокета и токен;
- на удалённой стороне `export CREDS_BROKER_SOCKET=…` и затем `creds ssh <token> -- uname -a`
  возвращает вывод, а модал согласия появляется **на локальной машине**;
- если права сокета не 600 — появляется предупреждение (на этом хосте не появится: там 600);
- повторный клик предлагает закрыть мост, и после закрытия сокет исчезает.

## 2. Фаза 4, переоценена 2026-08-26 — она НЕ «не начата»

Фаза 4 писалась как «удалённый родственник D1» при замороженном D1 и звучала как большая новая
работа: реализовать протокол `ssh-agent`, `SSH_AUTH_SOCK`, всё с нуля (Г-4 родительского плана).
**Эта формулировка устарела целиком.** D1 выпущен, и он сделал именно трудную половину.

### Что уже есть

| часть | где | состояние |
|---|---|---|
| протокол `ssh-agent`, подпись, согласие на каждое использование | `sshAgentServer.ts`, `sshAgentSign.ts`, `sshAgentManager.ts` | выпущено (D1) |
| ключ живёт только в памяти окна, умирает с ним | там же | выпущено |
| `SSH_AUTH_SOCK` в интегрированных терминалах | `sshAgentManager` | выпущено |
| **флаг `-A` (agent forwarding) в argv** | `sshOptions.ts:197`, галочка в форме, показ в просмотрщике | **выпущено (D7)** |
| транспорт до удалённого хоста | `sshBridge.ts` (фаза 3) | выпущено |

То есть механизм проброса агента на удалённый хост — это штатный `ssh -A`, и он **уже собирается**
обоими путями. Строить нечего.

### Что измерено 2026-08-26, и почему это меняет вывод

Не «фазу 4 надо построить», а **«фаза 4 на Windows построена и инертна»** — тот самый класс, что
теперь записан в [security.md](../.claude/rules/shared/common/security.md) как «мера, работу которой
вы не наблюдали».

1. **Расширение запускает `ssh` по PATH** — `sshExecRunner.ts:75`, `runBounded('ssh', …)`. На этой
   машине PATH даёт **MSYS-ssh из Git for Windows** (`C:\Program Files\Git\usr\bin\ssh.exe`,
   OpenSSH_10.3p1), а не встроенный (`C:\Windows\System32\OpenSSH\ssh.exe`, 9.5p2).
2. **MSYS-ssh не умеет named pipe.** Измерено сегодня, воспроизводит находку D1: с
   `SSH_AUTH_SOCK`, указывающим на pipe, `ssh-add` отвечает `Error connecting to agent: Bad file
   descriptor`. D1 это уже знал и записал: на Windows его агент обслуживает **встроенный** клиент.
3. **`SSH_AUTH_SOCK` нашего агента не попадает в окружение `ssh`, который порождает расширение.**
   Он ставится через `EnvironmentVariableCollection`, а это по контракту VS Code влияет на
   **терминалы**, не на процесс extension host. Порождённый `ssh` наследует `process.env`, где его
   нет.

Итог: галочка «Forward the SSH agent» есть, флаг до argv доходит, а агент, который он пробросил бы,
недостижим для клиента, которого мы запускаем. **Никто этого не заметит** — `-A` без достижимого
агента не ошибка, а тишина.

### Что из этого следует делать — и это не одна задача, а две разные

**4a. Remote-SSH — это ДЕФЕКТ, а не фича.** Починка маленькая и проверяемая:
   - запускать на Windows **встроенный** `ssh.exe` явно, когда он есть, а не первый по PATH — той же
     формы решение, что D1 уже принял для `gpg.ssh.program`;
   - класть `SSH_AUTH_SOCK` агента в окружение порождаемого `ssh`, когда агент запущен;
   - тест, который проверяет **эффект, а не присутствие флага**: с `-A` и живым агентом удалённый
     `ssh-add -l` видит ключ, и модал появляется локально. Присутствие `-A` в argv доказывает только
     отправку — ровно та ошибка, что уже стоила двух инертных флагов в этом же плане.

**4b. WSL — единственная настоящая стройка, и трюк фазы 2 здесь не работает.** WSL-путь CLI держится
на перезапуске Windows-бинаря через interop; **сокет перезапустить нельзя**. Нужен релей: unix-сокет
внутри WSL, проксирующий в Windows-pipe — это путь B (`creds relay`) родительского плана, который так
и не строился. Объём реальный: слушатель, проксирование в обе стороны, жизненный цикл с окном.

**Приоритет:** 4a вперёд. Он дешевле, он чинит уже отгруженное обещание, и до него WSL строить
незачем — если `-A` не работает и на Remote-SSH, релей в WSL просто донесёт до другого места ту же
тишину.

**Чего НЕ проверено:** воспроизвести измерение D1 «встроенный OpenSSH отвечает Node-pipe» сегодня не
удалось — мой пробник на игрушечном pipe-сервере не дождался подключения, и причину я не выяснил. Их
измерение делалось против настоящего `SshAgentServer` и остаётся в силе; моё — слабее, и опровергать
им чужое было бы ровно тем выводом-из-предположения, против которого написано правило. Перед 4a это
надо померить заново, против живого агента.
