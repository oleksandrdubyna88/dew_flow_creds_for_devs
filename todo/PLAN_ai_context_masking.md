## 1. Симптом

Разработчик работает с Cursor / Claude Code / Copilot / Aider. Самая частая утечка — не взлом, а
копипаста: человек вставил в чат вывод терминала или конфиг, а там оказался захардкоженный токен,
строка подключения к БД или приватный ключ. С брокером появляется второй, более коварный путь: агент
сам запускает команду через `ssh:exec` или `db:query`, и **вывод команды уходит агенту дословно** —
`sshUseActions.ts:170-176` возвращает `outcome` как `ExecResponseBody` без каких-либо преобразований.
Если команда напечатала пароль (`env`, `cat .env`, `terraform output`), пароль оказался в контексте
модели.

**Цель:** секрет из хранилища не может уехать в контекст модели через брокер; вместо него —
`<CREDS_MASKED:DB_PASSWORD>`.

## 2. Где именно перехватывать — одна точка

`credsAgentServer.handle` вызывает `this.respond(res, result.status, result.body)`
(`credsAgentServer.ts:259`) для **любого** действия. Это единственная точка, через которую проходят
все ответы, и она не знает о конкретных действиях — то есть маскирование там:

- покрывает `ssh:exec`, `db:query`, `script:run`, `terminal:run` сразу;
- **автоматически покроет любое будущее действие**, возвращающее текст;
- не требует правок ни в `sshUseActions.ts`, ни в `agentUseActions.ts`, ни в интерфейсе `UseAction`.

Ровно этим свойством («шов сработал как задумано») уже отличилось расширение брокера на пять новых
kind'ов в 0.52.0.

**Где маскировать НЕЛЬЗЯ:** в `agentCli.ts`. Он работает под обычным node **вне доверенной
границы** и по архитектурному инварианту должен остаться тупым ретранслятором. Маскирование в
клиенте означало бы, что немаскированные байты уже пересекли границу.

## 3. Таблица маскирования — и главный риск

Наивная реализация: собрать все секреты всех разблокированных аккаунтов и искать их в выводе. Это
воспроизведёт на горячем пути ровно ту стоимость, которую 0.57.0 только что убрал: «семь обращений в
keychain на сущность» (см. `syncIdle.ts` и его doc-comment про 7000 обращений раз в пять минут).

**Правильная область: секреты сущности этого гранта.** Для `ssh:exec` они **уже в памяти** к моменту
появления вывода — `entityFor` (`agentUseActions.ts:58-60`) и `prepareAuth` (`sshUseActions.ts:63-120`)
их только что прочитали в локальные переменные. То есть в типовом случае маскирование стоит **ноль
дополнительных обращений** к keychain.

Расширение области — только явным включением: настройка `credSshManager.maskingScope`:

| значение | что попадает в таблицу | стоимость |
|---|---|---|
| `grant` (по умолчанию) | секреты сущности гранта | 0 лишних чтений |
| `account` | все секреты аккаунта гранта | N чтений, кэш на TTL |
| `off` | ничего | — |

## 4. Что именно маскируется

Чистый модуль **`secretMasker.ts`** (`vscode`-free):

```ts
export interface MaskEntry { value: string; label: string; } // label = DB_PASSWORD, SSH_KEY…
export function buildMaskTable(entries: readonly MaskEntry[]): MaskTable;
export function maskText(text: string, table: MaskTable): { text: string; hits: number };
export function maskExecBody(body: unknown, table: MaskTable): { body: unknown; hits: number };
```

Правила, которые нужно решить заранее, иначе маскер сделает вид, что работает:

1. **Минимальная длина.** Значения короче ~8 символов не маскируются: пароль `1234` превратил бы
   любой вывод в решето (`<CREDS_MASKED>` вместо каждого номера строки). Короткие секреты — это
   отдельная проблема (политика PIN), не задача маскера. Порог — константа с объяснением.
2. **Подстрока, а не токен.** Искать надо именно подстроку: пароль может быть внутри URL, внутри
   base64, внутри JSON. Это значит O(len × entries) на вывод до 256 КБ — приемлемо, но замер нужен.
3. **Производные формы.** Как минимум: сам секрет; его URL-encoded вид; его base64. Приватный ключ
   маскируется целиком по маркеру PEM, а не по всему телу (иначе перенос строк ломает поиск).
   **Явно НЕ маскируем** хэши и «похожие» значения — эвристики дают ложные срабатывания и ломают
   вывод, что хуже, чем не сработать: агент получит испорченный `git diff` и будет чинить не то.
4. **Порядок.** Более длинные значения — первыми, иначе короткий секрет разрежет длинный.
5. **Метка стабильна.** `<CREDS_MASKED:DB_PASSWORD>` — из имени env-биндинга (`envBindings`), иначе
   из имени поля. Одинаковое значение всегда даёт одинаковую метку — иначе агент решит, что это два
   разных значения.

## 5. Что делать с буфером обмена — и почему почти ничего

В VS Code **нет** события «буфер обмена изменился». Перехвата чтения нет и быть не может. В
репозитории уже задокументировано и опубликовано в README, что Windows Clipboard History
захватывает значение в момент копирования, и последующая очистка до неё не доходит
(`secretClipboard.ts` умеет только TTL-очистку по записи).

Поэтому «фильтр буфера обмена» из исходной формулировки в этом плане **сознательно отклонён** как
невыполнимый в обещанном виде. Что реально можно и стоит сделать вместо этого:

- **Локальная проверка по требованию.** Команда `Check Clipboard for Secrets` — читает буфер один
  раз, по явному нажатию, и говорит, есть ли там значение из хранилища. Это честно: инструмент не
  утверждает, что следит непрерывно.
- **Скан открытого файла / выделения** (`Scan File for Vault Secrets`) — там события есть, и это
  ловит настоящую типовую утечку («вставил конфиг в чат»), причём до вставки.
- Опционально позже: диагностика (squiggle) на найденном секрете в редакторе — переиспользует
  `vscode.languages.createDiagnosticCollection`, ничего нового не требует.

Постановка при этом остаётся той, что уже принята в репозитории для `detectSecretPrints`
(`scriptRender.ts:195-214`): **предупреждать, не блокировать** — это код и данные пользователя.

## 6. Порядок сборки

1. `secretMasker.ts` + тесты (все правила §4, включая «не маскируем короткое» и «длинные первыми»).
2. Точка перехвата: `respond` в `credsAgentServer.ts` — маскирование `ExecResponseBody`-подобных
   полей; лог «masked N values» через уже существующий `deps.note`/audit-канал.
3. Таблица области: `grant` по умолчанию; настройка `maskingScope`; кэш на аккаунт с TTL для
   `account`.
4. Тесты брокера: пароль, напечатанный командой, не доезжает до тела ответа.
5. `Check Clipboard for Secrets` + `Scan File for Vault Secrets` + манифест.
6. CHANGELOG, README (с явной оговоркой про пределы буфера обмена), `module_extension.md`.

## 7. План тестирования

- Красный тест первым: `ssh:exec`, чья команда печатает пароль записи → в `body.stdout` его нет,
  есть `<CREDS_MASKED:PASSWORD>`; `hits === 1`.
- То же для `stderr`, для `db:query`, для `script:run`.
- Короткий секрет (< порога) **не** маскируется, и это зафиксировано тестом с объяснением.
- Секрет внутри URL и внутри base64 — маскируется (производные формы).
- Вывод без секретов проходит **байт в байт** (никаких ложных срабатываний) — на реалистичном
  образце: `git diff`, JSON, лог с хэшами.
- 256 КБ вывода × 10 значений — замер времени, записан в CHANGELOG.
- `maskingScope=off` полностью выключает; `grant` не делает ни одного лишнего обращения в keychain
  (тест со счётчиком, как в `treeProviderPasswordFlag`).
- Приватный ключ маскируется целиком, а не построчно.

## 8. Definition of Done

- [ ] Маскирование живёт **в одной** точке; `sshUseActions`/`agentUseActions` не изменены.
- [ ] `agentCli.ts` не содержит логики маскирования (он вне границы доверия).
- [ ] Область по умолчанию — `grant`, и тест доказывает отсутствие лишних чтений keychain.
- [ ] Ни одного ложного срабатывания на контрольном наборе вывода.
- [ ] README **прямо говорит**, чего маскирование не делает: не следит за буфером обмена
      непрерывно, не видит того, что агент прочитал файлом сам, не защищает от Clipboard History.
- [ ] Число замаскированных значений попадает в audit-канал.

## 9. Честная граница этой фичи

Маскирование вывода брокера закрывает ровно один канал: **вывод команд, которые запускает агент
через нас**. Оно не закрывает и не может закрыть:

- агент читает `.env` своим инструментом чтения файлов — мы этого вызова не видим;
- человек копирует и вставляет сам;
- секрет попал в контекст до того, как появился в хранилище.

Это стоит сказать в README ровно так. Фича, которая обещает «шилд от контекстных утечек», а закрывает
один канал из четырёх, опаснее отсутствующей: на неё начинают полагаться. Правильная формулировка —
«вывод команд, запущенных агентом через CredsForDevs, маскируется», и ничего больше.
