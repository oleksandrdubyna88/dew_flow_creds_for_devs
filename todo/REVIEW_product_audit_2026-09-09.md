## 1. Ошибка маскирования превращается в выдачу исходного секрета

**Код:** `src_vs_code/src/brokerResponse.ts:23`, `:33`, `:54`; `src_vs_code/src/credsAgentServer.ts:565`, `:574`, `:584`, `:593`; `src_vs_code/src/maskEntries.ts:52`.

`maskedBody` при исключении провайдера масок возвращает исходный `body` с `hits: 0`. `maskedReason` пользуется тем же путём. После выполнения команды broker отправляет этот body клиенту. Провайдер делает несколько чтений через `Promise.all`: отказ одного чтения отменяет подготовку всей таблицы масок, даже если другое секретное значение уже было использовано командой.

**Условие:** разрешённый action вернул секрет в stdout / сообщении драйвера, а последующее чтение для маскирования завершилось ошибкой. Получать разрешение на action атакующему этим багом не требуется обходить. Это также может случиться без атакующего, при обычном отказе хранилища.

**Воспроизведение:** искусственный action возвращал строку `synthetic-audit-password-ONLY`, провайдер масок выбрасывал исключение. Реальный HTTP broker ответил `200` и исходной строкой. Отдельно `maskedReason` вернул ту же строку без редактирования. Это подтверждает путь утечки в ответ и небезопасный результат подготовки текста для журнала; реальный драйвер с рабочим паролем не запускался.

**Исправление:** готовить таблицу для фактически используемых значений до запуска и удерживать её до завершения запроса. При невозможности безопасно обработать результат выдавать нейтральную ошибку без stdout/stderr и без сырого exception в журнале. Отдельно сообщать, что действие могло уже выполниться, чтобы клиент не повторил побочный эффект автоматически. Потеря маскирования должна быть видимым состоянием, а не `hits: 0`.

**Проверка исправления:** отказ каждого чтения, смена/удаление записи во время action, секрет в успешном выводе и исключении; ни ответ, ни журнал не содержат исходного значения.

## 2. Современный envelope допускает снятие MAC и изменение wraps

**Код:** `src_vs_code/src/cryptoUtils.ts:437`, `:460`, `:637`, `:647`, `:667`; `src_vs_code/src/syncManager.ts:445`, `:453`; `src_vs_code/src/vaultKeys.ts:420`, `:426`.

Запись v4 всегда создаёт MAC, покрывающий в том числе wraps. Однако отсутствие поля MAC считается `missing` без проверки версии, а `macStatusBlocksSync` блокирует только `bad`. AAD зашифрованного payload не включает wraps. Поэтому удаление MAC снимает отдельную проверку целостности методов открытия.

**Условие:** возможность изменить envelope в sync location, например доступ на запись к общему каталогу или компрометация blob-сервера. Для самого изменения PIN/master key не нужны. Это не даёт расшифровать payload без существующего ключа.

**Воспроизведение:** создан envelope v4, из его wraps удалена одна синтетическая запись и удалён MAC. Результат реальных функций:

```text
version=4; macStatus=missing; blocksSync=false;
payloadOpens=true; wrapsRemaining=1
```

Payload остался корректно расшифровываемым. В `syncProfile` такой статус не останавливает цикл. Потеря реальной security/recovery wrap на всех устройствах целиком не воспроизводилась: итог также зависит от локального key cache и последующей записи. Но проверка, которая должна не позволять принять изменённые wraps, достоверно обходится.

**Исправление:** требовать MAC для версий, которые его обязаны иметь; legacy-миграцию выделить в явный путь. После unwrap держать ключ и wraps в промежуточном состоянии, проверять целостность и только затем обновлять доверенный cache. Изменения version/header должны по-прежнему проверяться AAD. Одна проверка формата должна применяться к sync, import и recovery.

**Проверка исправления:** удалённый MAC, MAC другого типа, изменённая/удалённая wrap, неподписанный legacy-файл, свежий и прогретый cache. Отказ не должен переписывать файл, перечень методов открытия или доверенное состояние.

## 3. Лимит числа вызовов grant не атомарен

**Код:** `src_vs_code/src/credsAgentServer.ts:494`, `:510`, `:554`, `:563`, `:622`; `src_vs_code/src/grantRegistry.ts:142`, `:156`; `src_vs_code/src/grantLimits.ts:15`.

Grant проверяется до чтения тела и ожидания согласия. Несколько первых запросов совместно ожидают один диалог. После Allow каждый выполняет `touch`, но повторной проверки / атомарного резервирования остатка вызовов нет.

**Воспроизведение:** `agentGrantMaxCalls=1`, два POST к одному токену, один отложенный Allow. Получено:

```text
configuredMaxCalls=1; executed=2; dialogs=1; statuses=[200,200]
следующий запрос: 401
```

Это не обход самого человеческого согласия, но нарушает установленный им лимит. Дополнительный риск рядом: one-use запись удаляется только после отправки результата (`credsAgentServer.ts:587`), поэтому её жизненный цикл тоже требует защиты от параллельных действий. Этот отдельный сценарий удаления записи не объявляется воспроизведённым данным тестом.

**Исправление:** после consent атомарно проверить актуальность grant и зарезервировать использование до запуска. Определить, что расходует лимит при отказе/таймауте/ошибке и как учитывается действие, которое уже могло выполниться. Для одноразовых сущностей сериализовать использование по записи, включая обращения через разные grants и двери broker.

**Проверка исправления:** конкурентные запросы с cap=1, истечение во время диалога, разные токены одной one-use записи, отмена и исключение после запуска. При cap=1 второй action не начинается.

## 4. DELETE может сообщить успех, оставить vault и удалить его login key

**Код:** `src_minimalapi_server/src/VaultStore.cs:175`; `src_minimalapi_server/src/Program.cs:889`, `:893`, `:907`, `:915`, `:917`.

`DeleteEverythingFor` подавляет `IOException` и `UnauthorizedAccessException`, не возвращая результат. Endpoint затем удаляет запись участника и login key S и отвечает `204`. Комментарий endpoint об удалении ключа только после исчезновения vault не обеспечен проверкой.

**Воспроизведение:** на Windows открыт искусственный `.bin` без разрешения совместного удаления. `DeleteEverythingFor` завершился без исключения, но `File.Exists(vaultPath)` остался `true`. Вызов HTTP endpoint с этим отказом отдельно не выполнялся; продолжение удаления ключа и безусловный `204` установлены по коду.

**Последствия:** ложное подтверждение удаления данных. В корпоративном режиме оставшийся vault может лишиться S, необходимого обычному пути открытия; возможность восстановления зависит от наличия рабочих recovery wraps/копий. На Linux незакрытый дескриптор сам по себе обычно не препятствует unlink; там условие — соответствующая ошибка доступа/файловой системы, а не Windows-механизм блокировки.

**Исправление:** результат удаления по компонентам, подтверждение исчезновения vault перед удалением S, повторяемая операция с состоянием завершения. Защитить удаление и запись одной областью синхронизации: сейчас запись использует `GateFor`, удаление его не берёт. Политика удаления backup должна описываться отдельно от удаления текущего vault.

**Проверка исправления:** заблокированный файл, отказ доступа, повтор DELETE, запись одновременно с удалением, crash между шагами. Если vault остался, ключ остаётся и API не сообщает полное завершение.

## 5. Два первых sync могут без конфликта перезаписать друг друга

**Код:** `src_vs_code/src/serverTransport.ts:237`, `:240`, `:250`, `:255`; `src_minimalapi_server/src/Program.cs:853`; `src_minimalapi_server/src/VaultStore.cs:64`, `:82`.

После `404` transport удаляет сохранённую версию. Следующий PUT не содержит ни `If-Match`, ни `If-None-Match`. Два устройства, прочитавшие отсутствие vault, оба делают безусловную запись. Сервер уже умеет проверять отсутствие, но клиент не передаёт это условие.

**Воспроизведение:** два реальных `ServerTransport`, подменённый fetch с двумя `404`, затем две записи. В обеих запросах оба conditional header отсутствовали; последнее содержимое заменило первое. Это транспортный тест, не полноценный end-to-end прогон двух SyncManager. Семантика сервера подтверждена чтением `VaultPrecondition` и `TryWriteVaultAsync`.

**Последствия:** потеря первой серверной версии на первоначальном sync / восстановлении после удаления. Локальная копия первого устройства может впоследствии вернуть данные, поэтому необратимая потеря не утверждается для каждого случая.

**Исправление:** различать `not read`, `absent`, `present(etag)`. После подтверждённого `404` отправлять `If-None-Match: *`, при `412` перечитывать и объединять. Не превращать ошибку/утрату ETag в разрешение на безусловную запись. Именно для конкурирующего создания предусмотрено это условие в [RFC 9110, If-None-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2).

**Проверка исправления:** два клиента одновременно читают `404`; первая запись успешна, вторая получает `412`; последующий merge сохраняет обе независимые записи.

## 6. Недоверенный blob управляет стоимостью KDF до аутентификации

**Код:** `src_vs_code/src/cryptoUtils.ts:85`, `:150`, `:167`, `:180`, `:386`, `:400`; `src_vs_code/src/keyWrap.ts:376`, `:383`; `src_vs_code/src/syncManager.ts:445`, `:453`.

`paramsOf` принимает числовые `kdfN/kdfR/kdfP` из файла, без своего разрешённого диапазона или списка поддерживаемых профилей. `maxmem=300 MiB` ограничивает память, но не является пределом времени вычисления. KDF нужен для unwrap до проверки MAC.

**Воспроизведение:** повреждённый синтетический blob с корректными длинами salt/IV/tag, `N=1024`, `r=8`; изменение `p` с 1 на 128 увеличило время вызова примерно с **3 до 213 мс**, после чего оба варианта сообщили `wrong-password`. Это ограниченный локальный замер, не нагрузочная оценка корпоративного сервера и не заявление о конкретном времени при больших параметрах.

**Условие:** пользователь открывает/импортирует изменённый зашифрованный blob или пытается разблокировать изменённый vault. Синхронные пути удерживают event loop; асинхронный unwrap занимает libuv worker, а не напрямую блокирует JS-поток. Обе формы затрат описаны в [официальной документации Node.js crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

**Исправление:** проверять целочисленные параметры и поддерживаемые KDF-профили до вычисления, задавать бюджет операций и число одновременно исполняемых unwrap. Не снижать стоимость шифрования новых данных ради этой защиты. Для жёсткой отмены дорогих входных задач использовать исполнение, которое можно остановить: таймаут Promise сам по себе расчёт не прерывает.

**Проверка исправления:** большие/дробные/отрицательные значения, неожиданная комбинация N/r/p, несколько запросов параллельно; отказ до запуска дорогого KDF, сохранение совместимости с выпущенными форматами.

## 7. Целый архив не обязательно является согласованной резервной копией

**Код:** `src_minimalapi_server/src/BackupArchive.cs:26`, `:106`, `:173`, `:184`, `:205`; `src_minimalapi_server/src/BackupRunner.cs:242`; `src_minimalapi_server/src/LoginKeyStore.cs:75`.

Архив строится обходом живого дерева без общего snapshot. Atomic rename гарантирует целостность отдельного файла, но не согласованность vault, login key, roster и конфигурации. Проверка архива аутентифицирует содержимое и имена, не проверяя соответствие зависимых состояний.

**Воспроизведение:** настоящие `BackupArchive.CreateFile`, `Verify`, `Extract`. Через callback `onEntry` между чтением `org/login-keys/` и `vaults/` атомарно заменены два синтетических зависимых файла. Verify прошёл, после Extract получено:

```text
restoredFactor = generation-1
restoredVault = requires-generation-2
```

Маркеры моделировали зависимость, реальный пользовательский vault не расшифровывался. Подтверждено смешение поколений файлов; невозможность открыть конкретный корпоративный vault в таком архиве — вывод из зависимости от S. Реалистичный сходный случай: новый сотрудник впервые получает S и пишет vault, когда архив уже прошёл каталог ключей, но ещё не прошёл каталог vault. Его vault может попасть в копию без соответствующего ключа.

**Исправление:** выбрать согласованный snapshot: snapshot файловой системы, согласованное поколение данных / manifest с удержанием поколений либо короткая пауза мутаций при получении копии для дальнейшего архивирования. Дополнить проверку архива проверкой зависимостей на выделенном стенде восстановления. Долгая блокировка всех операций на время сжатия — не обязательное решение.

**Проверка исправления:** первое зачисление сотрудника, удаление/повторное создание, изменения recovery metadata во время backup. Копия должна представлять допустимое состояние системы; статус «восстановление проверено» требует отдельной проверки, одного Verify недостаточно.

## 8. Полный набор тестов сейчас не проходит и зависит от окружения

**Код:** `src_vs_code/src/test/sshProgram.test.ts:25`; `src_vs_code/src/test/sshCommand.test.ts:96`; `src_vs_code/src/sshProgram.ts:83`, `:112`, `:132`. Дополнительные различия runtime проявились в `configFieldsOutcome.test.ts` и `configValidation.test.ts`.

На Windows два SSH-теста ожидают абсолютный путь, но не задают PATH-probe. Когда первым в PATH уже находится системный OpenSSH, продукт обоснованно возвращает `ssh`, и тест падает. Это дефект изоляции проверки, не доказательство неработающего SSH forwarding.

В WSL с Node 20 SSH-проверки прошли, но два теста координат ошибки JSON не получили ожидаемые line/column. На Windows с Node 24 эти тесты прошли. Отдельно проверять поддержку Node 20 продуктом и объявлять регрессию UI на основании этого прогона нельзя; подтверждено различие тестового контракта между runtime.

**Исправление:** передавать probe во все проверки построения SSH-команды, фиксировать поддерживаемую тестовую матрицу и отдельно проверять адаптеры ОС. Парсинг диагностик JSON проверять на явных fixtures сообщений разных поддерживаемых runtime, а полную цепочку — в runtime целевого extension host. Не заменять это удалением неудобных assertions.

Не выполнялись полноценные нагрузочные испытания, реальный login корпоративного IdP, аппаратный WebAuthn, восстановление рабочих секретов и проверка установленного в компании deployment. Поэтому отчёт не устанавливает фактическую компрометацию, пропускную способность, p95 или полный уровень защищённости действующего сервиса.

## Что сохранить и что улучшать

Сохранить разделение криптографических функций, key/session management, транспорта и серверного opaque storage; реестр действий broker; отдельные CLI/MCP hosts. Удачны ETag под серверной блокировкой, атомарная запись отдельных файлов, staging при restore и большой набор тестов. Ошибки выше требуют более сильных контрактов на границах этих частей, а не переписывания продукта.

Практический порядок: устранить выдачу немаскированного результата и обход MAC; атомарно учитывать grants; согласовать удаление и backups; затем закрыть first-write CAS и KDF-бюджеты. Стабилизацию тестовой матрицы выполнять вместе с первыми исправлениями.

Отдельный [backlog улучшений](PLAN_product_improvements.md) описывает контроль доступа при увольнении, подтверждённое восстановление, наблюдаемую синхронизацию, управление AI-разрешениями, ротацию секретов и дальнейшее развитие кода/тестов.
